## 问题与修复的必要性 {#problem}

合法 LDAP 账号也可能拥有很长的可分辨名称（Distinguished Name，DN），尤其是姓名和多级组织单元中包含中文、俄文等非 ASCII 文本时。
一个通过组获得权限的用户，可能既不需要直接绑定用户策略，也没有本地父身份记录；但登录流程仍会尝试读取这些可选记录。
故障发生在规范化 DN 被用作对象后端的目录名或文件名之后：路径分量无法保存，名称过长错误向上传播，最终让合法用户登录失败。

这里不是 LDAP 拒绝了账号名称或密码，而是外部身份与 SILO 内部存储键发生冲突。
同类错误还可能影响 STS 签发、服务账号创建和凭证加载。
修复既要恢复可用性，也必须守住[持久 IAM 撤销机制](/zh/blog/design/iam-revocations/)的安全边界。

## 名称为什么会变长 {#normalization}

DN 标识整个目录条目，例如 `cn=张三,ou=研发,dc=example,dc=com`，并不只是登录用户名。
这里的转义格式是 **`\xx`：反斜杠加两位十六进制数字，表示一个字节**。
它不是连字符，也不是每个 Unicode 字符只对应一个转义。

[RFC 4514 §2.4](https://www.rfc-editor.org/rfc/rfc4514.html#section-2.4) 要求转义某些语法字符，并允许转义其他字符。
普通 UTF-8 文本可以直接保留；标准没有要求所有非 ASCII 字符都转义，也没有规定唯一的 DN 规范字符串。

把非 ASCII 的 UTF-8 字节逐个十六进制转义，是 `go-ldap` 库 `DN.String()` 的序列化选择。
SILO 的 `NormalizeDN` 先解析 DN，再调用这个序列化器，使属性类型名称和转义写法保持一致。
这是库选定的字符串表示，不代表所有 LDAP 身份等价关系都能简化为字符串相等。

| 表示方式 | 字节数 |
| --- | ---: |
| UTF-8 字符 `张` | 3 |
| 序列化后的 `\e5\bc\a0` | 9 |
| `cn=` + 40 个 `张` + `,dc=example,dc=com` | 序列化前 141 |
| 同一个完整 DN 序列化之后 | 381 |

后两项已用验收时的依赖实际运行核对。身份本身没有变化，变长的是表示形式。
当这段文本被用作文件名时，文件系统看到的是展开后的实际字节。
按解码后的汉字数计算，不能让实际文件名装进存储限制。

这条查询结果规范化路径由 MinIO 上游在 2024 年 3 月 27 日引入，提交为
[`minio/pkg efb73fa5`](https://github.com/minio/pkg/commit/efb73fa5d52fc1f217c58d51544f448e3862ab61)，
作者是 Aditya Manthramurthy（@donatello）。配套的 [MinIO PR #19358](https://github.com/minio/minio/pull/19358)
解释了身份一致性的需要：采用 LDAP 服务端返回的 DN，而不是假定用户输入的拼写就是权威身份。
该 PR 的例子是用户输入 Unicode 变体句点，目录查询后返回普通句点。
SILO 继承了这条路径；九月的撤销修复没有新引入这种转义。

## 登录回归如何形成 {#cause}

对象 IAM 后端使用如下路径：

```text
config/iam/users/<normalized-DN>/identity.json
config/iam/policydb/sts-users/<normalized-DN>.json
```

相关限制针对**单个路径分量**，不是整个 DN 的字符总数。
当 DN 占据一个分量时，策略映射的 `.json` 后缀也要计入：250 个 ASCII 字节加后缀刚好是 255，251 加后缀就超限。

两个继承行为让症状更加复杂。首先，`checkPathLength` 在 Unix 上不统计反斜杠。
复现中的 271 字节转义 DN 被它算成 197，因此能通过预检查，却可能在文件系统层失败。
其次，如果祖先目录不存在，文件系统可能尚未检查到过长分量就先返回文件缺失。
IAM 前缀目录是否已经存在，因此会改变结果。目录状态是复现条件，不是修复手段。

| 变更 | 对故障的影响 |
| --- | --- |
| MinIO [`ee9077db`](https://github.com/minio/minio/commit/ee9077db7d5f23de17cedbb6d7e7c99b1638ad6e)，2020 年 5 月 | 引入路径长度预检查在 Unix 上漏计反斜杠的行为。 |
| MinIO [`280526ca`](https://github.com/minio/minio/commit/280526caf7e41881f7cd9a3c97028e1f56df41ef)，2024 年 3 月 | 策略缓存未命中时，磁盘回读错误开始向上传播，构成更早的失败路径。 |
| MinIO 规范化及 [`7e45d84a`](https://github.com/minio/minio/commit/7e45d84acebf9eac5391ec7676c4a7f92e52fd75)，2024 年 3 月 | 身份和映射采用规范化 DN，非 ASCII 内容可能展开。 |
| SILO [`709d50a9`](https://github.com/pgsty/silo/commit/709d50a916bf3311eda2b3882ac5f2a0251f4223)，随 Server 20260916 发布 | 为撤销和重放防护增加持久父身份版本读取，让登录流程新增一条必经读取路径。 |

未修复实现中，271 字节样本在 users 前缀目录不存在时返回 HTTP 200，存在时返回 HTTP 500。
修复后两种状态都返回 HTTP 200，测试中的 S3 和服务账号操作也通过。
384 字节 DN 则同时覆盖了更早的策略读取失败路径。

这些原因具有不同历史。九月改动引入了父身份读取回归，但回退到更早版本并不能证明所有长 DN 都受支持。
历史归因核对了源码与发布祖先关系，没有运行历史发布二进制。

## 决策：只将确定无法保存的记录视为不存在 {#decision}

修复集中在对象 IAM 的共享读取函数
[`loadIAMConfigBytesWithMetadata`](https://github.com/pgsty/silo/blob/d43adc0f2bf1c2cfd174fbcb63bfa3ed443680b0/cmd/iam-object-store.go#L137)。
先按原流程读取；仅当读取失败，并且**同时满足三个条件**时，才转换为 `errConfigNotFound`：

1. 错误是 `errFileNameTooLong` 或 `ObjectNameInvalid`，包括能识别的包装错误。
2. 完整对象键通过正常的桶名、对象名合法性验证。
3. 至少一个按斜杠分隔的路径分量完全由 ASCII 构成，并且超过 255 字节。

实现同时检查 `len(component) > 255` 和 `utf8.RuneCountInString(component) == len(component)`。
第二项只是确认路径分量全部是 ASCII，**没有把 `\xx` 解码后再比较，没有改按原始用户字符数计长，也没有放宽文件系统限制**。
规范化后的转义 DN 满足 ASCII 条件；检查完整键也自然涵盖文件后缀。

在这个狭窄条件下，记录无法保存到请求的路径分量，因此调用者可以继续使用已有的“记录不存在”处理：
例如通过组策略授权，而不要求用户一定有专属策略文件。
LDAP 认证和权限校验仍然执行，没有增加默认授权，也没有跳过父身份版本检查。

成功读取后的解密、解析和索引处理沿用原流程；其他错误继续向上传播。
写入、删除、etcd 后端和全局路径长度检查不变。
最终 PR 的核心生产逻辑新增 25 行，回归测试新增 318 行。
没有新增存储格式、迁移、配置开关、后台任务或额外 I/O；额外的名称扫描只发生在读取失败后，复杂度随路径长度线性增长。

## 为什么原始分类还需要收窄 {#safety}

原 PR 将语法合法键上的 `ObjectNameInvalid` 归类为不存在。
这个范围过大：长度错误不总能证明记录从未存在。

一个反例是在 macOS 上先写入真实撤销记录，再把数据目录移到更深的位置。
键的各个分量仍未超限，相对路径读取也能证明记录还在，但完整路径限制使通常的读取失败。
如果把失败吞成不存在，就可能忽略已有撤销，让父身份检查通过。最终修复保留这个错误。

仅比较 UTF-8 字节数也不够。在 macOS 实验中，100 个 `界` 组成的分量虽然占 300 字节，仍然可以保存。
不能仅因字节数大于 255，就认定这种已有记录不可能存在。
ASCII 条件避免了对 Unicode 文件名做出这个错误推断。

因此，安全规则是：**已经证明不存在的记录，可以走原有缺失分支；可能存在、但当前读不到的撤销记录，必须继续报错。**
这也是修复能恢复登录，又不普遍忽略 IAM 存储故障的原因。

## 备选方案与取舍 {#alternatives}

| 方案 | 决策与原因 |
| --- | --- |
| 在共享对象 IAM 读取处做窄范围分类 | 采用。覆盖相关调用者，保留真实故障处理，不改变存储键。 |
| 将合法键的所有名称错误当作不存在 | 否决。完整路径过长可能掩盖已经存在的记录。 |
| 按解码字符数计长，或不计转义开销 | 否决。文件系统需要保存的就是展开后的名字。 |
| 只修正全局反斜杠计数 | 单独不足以解决本问题。只会更早拒绝同一名称，还影响普通对象路径，不能恢复登录。 |
| 保留原始 UTF-8，替换当前序列化输出 | 暂不采用。可以缩短部分名称，但会改变已有身份／映射键，也消除不了路径分量限制。 |
| 跳过父身份检查或回退持久撤销机制 | 否决。会牺牲撤销与防重放能力，并保留更早的策略读取失败。 |
| 用短键或哈希键存储，完整 DN 放入记录 | 有完整长身份持久化需求时另行设计。需同时处理查找、列举、迁移、导入导出、复制和混合版本。 |

删除 IAM 目录以获得文件缺失结果也不是修复：它会破坏状态，并依赖偶然的路径查找顺序。

## 保留的边界与运维建议 {#limits}

本决策恢复已验证的登录／读取路径，**没有让对象后端支持任意长度的身份记录写入**。
路径分量过长的直接策略映射和父身份版本记录仍会保存失败。
不能因此推导出需要此类写入的父身份级撤销操作已经受支持。
既有的逐 access key／token 撤销属于独立机制，应按其文档范围使用，并在相关端点验证拒绝结果。

受影响部署可以使用组授权，但组映射自身也必须能保存，并应部署已经验证包含此合并的 Server 制品。
验收应覆盖受影响用户的 STS 登录、签名 S3 访问、服务账号行为，以及可保存撤销记录的身份所对应的旧凭证拒绝。
不要删除 IAM 元数据或关闭撤销检查来绕过故障。
本补丁不引入数据迁移，既有[升级与恢复要求](/zh/operations/replication/iam-upgrade/)仍然适用。

这次设计的经验是：外部身份语法与内部存储命名应当分开。
当存储限制进入认证流程时，必须先明确一个错误究竟证明了什么，再改变它的含义。
本次最小且充分的修改，是有明确依据的缺失分类；完整长 DN 持久化仍是另一个问题。
