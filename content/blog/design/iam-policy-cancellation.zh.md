**设计决策，2026-10-23：** 在鉴权缓存锁之外加载策略替换结果，同时保留 IAM 写入顺序；把请求取消信号传到实际解密操作；保留调用者的时间预算，不给整个查询新增 30 秒上限。实现记录于提交 [`1b5477f3d`](https://github.com/pgsty/silo/commit/1b5477f3df87924712ad8dc580c8f8eac63eda2d)。本文是源码设计与验收记录，不代表某个发行版本已经包含修复，也不代表生产环境已经完成部署验收。

这项工作源自 [Server #251](https://github.com/pgsty/silo/issues/251)。受控复现区分出了两个服务端机制，尚不能据此认定报告中所有 Console 表象都来自同一个原因。

## 两种表现，两条因果链 {#symptoms}

管理员查看全部策略时，KES 响应很慢。策略请求耗时几秒，其他普通用户访问无关对象的请求也一起停住。另一个现象是，客户端已经放弃 SSE-S3 对象列表，服务端却继续向 KES 请求解密后续对象的密钥。

| 观察到的表现 | 已验证的机制 | 所需修复 |
| --- | --- | --- |
| 普通用户的 GET、HEAD、PUT 等待慢策略列表结束 | 列表在读取和解密策略期间一直持有鉴权缓存写锁 | A：把慢加载移出这把缓存锁 |
| 请求取消后，解密仍继续进行 | 中间层换用了后台 context，请求取消无法传到 KES | B：贯通受影响调用链中的请求 context |
| 原先成功的慢查询在第一版修复中约 30 秒后失败 | 复用的包装函数和新贯通的 context，把时间预算施加到了更大的操作范围 | R1：让每个期限继续只约束原来负责的操作 |

前两个缺陷需要分别处理。缩小锁范围不会自动终止被放弃的工作；只修复取消，也不能让健康请求在慢查询仍合法进行时使用权限缓存。

## 耦合是怎样形成的 {#cause}

`ListPolicies` 和 `ListPolicyDocs` 会重新加载持久化策略，并替换缓存中的策略映射。原实现从 `store.lock()` 开始，一直持锁到后端读取和解密结束。对象后端逐个加载策略文档，加密文档可能各自需要一次 KES 调用。普通鉴权通过读锁读取同一缓存，因此后端延迟会转化为无关请求的延迟。

取消链上还有独立的断点：配置解密使用了与请求无关的 context；SSE-S3 列表调用不接收 context 的单对象辅助函数；KES 适配器最终用 `context.Background()` 调用 `Decrypt`。上层函数接收了 context，并不代表真正发出去的请求继承了它。

这些证据指向锁的持有范围和 context 传播，并没有证明需要替换策略解析方式或加密算法。

## A：释放缓存锁，保留写入顺序 {#cache}

两把锁负责不同的事情：

- 缓存锁保护普通鉴权读取的内存数据。
- `writeMu` 保持 IAM 写入和缓存替换的顺序；列表准备替换结果时继续持有它。

最终执行顺序如下：

```text
获取 IAM 写串行锁和缓存锁
  只释放缓存锁
  使用调用者 context，把策略读取、解密到私有 map
  重新获取缓存锁
  再次检查加载结果和取消状态
  成功时补齐内置策略，发布完整替换结果
释放缓存锁和 IAM 写串行锁
```

加载期间，普通鉴权可以继续使用已经提交的缓存，其他 IAM 写入则保持原有执行次序。如果两把锁都释放，较早开始、较晚结束的列表就可能用旧快照覆盖新的权限更新或删除。要安全地允许这种并发，需要额外的版本校验或重试协议；当前修复不需要引入它们。

只有加载成功，并且在缓存锁内完成最后一次 context 检查，才发布替换结果。后端错误、只加载了部分数据，或在发布前观察到取消，都会保留原策略映射与更新时间。只在重新加锁之前检查取消还不够：请求可能恰好在等待这把锁时被取消。这是一个明确的取消检查边界，不承诺取消事件与随后每条指令之间存在全局原子顺序。

后台刷新也必须遵守原有合并与撤销规则。测试直接执行实际 `IAMObjectStore` 的刷新路径，避免仅用包装接口时绕过对具体后端类型的判断。成功与取消两种重载都与更新、策略删除、按范围 STS 撤销并发执行。持久化版本和防重放语义仍以[持久化 IAM 撤销设计](/zh/blog/design/iam-revocations/)为准。

## B：让取消真正到达执行中的工作 {#cancellation}

受影响的调用链现在保留调用者的 context：

```text
IAM / 配置请求
  -> 对象或 etcd 配置解码
  -> 配置解密
  -> KMS.Decrypt -> KES.Decrypt

SSE-S3 列表请求
  -> UnsealObjectKeys
  -> 接收 context 的单密钥辅助函数
  -> KMS.Decrypt -> KES.Decrypt
```

既有单对象 `UnsealObjectKey` 入口保留原签名。列表改用内部接收 context 的辅助函数，避免要求没有请求 context 的其他调用者一起改变接口。

列表迭代与缓存发布边界也检查取消。尤其是 IAM 解密被取消后，不得再启动历史 associated data（AAD，附加认证数据）回退。对于仍然有效的请求，旧密文所需的回退路径继续可用；兼容性判断与取消判断各自独立。密文格式、AAD、对象密钥顺序，以及非取消情况下的既有 KES 错误映射都保持不变。

取消不能撤回远端已经完成的工作。验收要求是：取消能够到达正在执行的请求，阻止后续解密和回退，并返回相应 context 错误；不要求从取消发生到本地函数返回之间耗时为零。

## R1：时间预算必须保留原来的作用范围 {#budgets}

第一版 A/B 修复复用了 `withIAMStorage`，让慢操作期间能够释放缓存锁。但这个函数还会创建超时。它来自 9 月 15 日的撤销持久化修复 [`709d50a916`](https://github.com/pgsty/silo/commit/709d50a916bf3311eda2b3882ac5f2a0251f4223)，当时限制存储操作、锁等待和清理耗时有明确用途。错误在于把它的锁处理行为与超时行为一并用于策略列表，而策略列表原来没有这一整批时限。

对抗性反例很直接：原始版本的慢策略查询在 32.74 秒后返回 HTTP 200，第一版候选却在 31.22 秒后返回 503。新增期限在 30 秒到期，退出过程和既有重试行为还可能推迟最终响应。这个新增上限既不是 A 生效的必要条件，也不是 B 生效的必要条件。

只去掉外层上限，对 etcd 仍然不够。etcd 原有子 context 用于限制 `Get` RPC；原来的解密实际上忽略了这个 context。B 贯通取消时，如果直接使用这个子 context，就会让同一截止时间继续限制已经读取成功之后的解密。于是，一次快速 `Get` 加上 32 秒解密，也会从成功变成失败。策略文档和策略映射都必须在读取结束后使用正确的父 context。

| 时间预算 | 最终归属与行为 |
| --- | --- |
| 调用者的 deadline 或主动取消 | 约束整个请求及其解密工作 |
| 既有 etcd 读取预算，通常为 30 秒 | 约束 `Get`，不再成为后续解密的额外期限 |
| 既有版本写入、撤销、分布式锁和清理预算 | 保留原包装函数与原有行为 |
| 被否决候选新增的整批策略列表时限 | 从两个策略列表入口移除 |

更短的调用者期限仍然有效，因为 etcd 读取 context 是请求 context 的子级。etcd 读取完成，也不意味着后续工作获得无限时间；解密继续遵守调用者剩余的预算。反过来，调用者允许查询运行更久时，超过 30 秒仍然可以成功返回。

这里的通用教训是：即使没有修改超时常量，修复 context 传播也可能改变超时行为。审查必须逐层核对 context 的含义，包括那些过去实际上没有被下层遵守的期限。

## 讨论过的替代方案 {#alternatives}

| 替代方案 | 未采用的原因 |
| --- | --- |
| 继续持有缓存锁，只缩短列表超时 | 健康请求仍会等待，合法慢查询还会新增失败 |
| 加载时释放全部 IAM 锁 | 旧结果可能覆盖后续写入；正确的乐观替换协议属于更大的设计 |
| 直接返回缓存策略，不再重载 | 改变管理查询的新鲜度语义，并掩盖加载问题 |
| 把整批上限改成更大的固定值 | 只是把兼容性失败推迟到另一种策略数量或 KES 延迟 |
| 只移除两个外层超时 | 无法解决 etcd 读取完成后的解密期限回归 |
| 删除全部后端超时 | 无必要地放宽已有读取、写入、锁等待和清理保护 |
| 并行解密或引入新缓存 | 涉及吞吐、调度、一致性与资源控制，A/B/R1 并不依赖这些机制 |
| 顺便重写 KES SDK 的重试行为 | 将依赖行为的变更带入服务端缺陷修复；本次验证已有重试边界并说明限制即可 |

相对于被测基线，最终 A/B/R1 生产代码共涉及 8 个文件，新增 83 行、删除 29 行。文件分布主要来自在内部调用点逐层传递 context。R1 本身相对于第一版候选，只修改两个生产文件，新增 12 行、删除 7 行。另有 5 个测试文件配套覆盖。无需修改依赖、线协议、密文格式或权限模型。行数说明变更范围，必要性则由反例证明，不能仅靠行数判断。

## 证据与回归契约 {#verification}

受控基线为 [`a07d655dc`](https://github.com/pgsty/silo/commit/a07d655dc69cf04b130c2634d9fa5301078af546)。相同的进程级实验直接复用到最终源码构建结果。以下数字来自本机测试夹具，不是生产延迟承诺。

| 场景 | 修复前 / 被否决候选 | 最终实现 |
| --- | --- | --- |
| 慢策略列表期间的四个普通用户对象请求 | 平均 5,284 ms | 平均 2.25 ms；策略列表本身仍耗时 5.23 秒 |
| 相同普通请求仅允许客户端等待 200 ms | 四个全部超时 | 四个均在 1.11–1.82 ms 内返回 200 |
| SSE-S3 列表在 200 ms 被客户端放弃 | 客户端退出后又启动 21 次解密 | 退出后新增 0 次；总共启动 4 次，观察期结束时无活动请求 |
| 对象后端的策略查询超过 30 秒 | 原始版：32.74 秒后 200；第一版候选：31.22 秒后 503 | 32.75 秒后 200，完整返回 61 个策略 |
| etcd 读取很快，解密需 32 秒，调用者预算 60 秒 | 候选错误地限制读取之后的解密 | 两个策略列表入口和策略映射加载均成功，读取仍保留 30 秒预算 |
| 正常与拒绝访问的 HTTP 对照 | 原始状态码、错误码与返回数量 | 51 项全部一致，包括分页、KMS 拒绝与签名检查 |

最终本地验收包括：

- 36 个正式定向场景和 23 个补充对抗性场景，各执行三轮 race 检查，无跳过、无竞态报告。
- 29 个既有 IAM 版本/撤销场景，以及 64 个配置、加密、KMS 场景通过 race 检查。
- 5 项负对照：只把 R1 的两个生产文件替换回第一版候选，五项预算检查全部失败。此前分别移除 A 或 KES 取消传播，对应检查也会失败。
- 全量测试 52 个包通过，8,227 条通过记录，168 条既有跳过。这是 Go 测试事件数量，包含父测试，不等于独立场景数；本次新增目标回归未跳过。
- 单独启用既有 etcd 并发、IAM 管理、STS 套件，12 个后端/服务器组合全部通过，无失败或跳过。
- `make verifiers` 和 `make build` 通过；可选 `typos` 工具未安装，未计为已执行。

全量首跑在未修改的 endpoint 测试中遇到 `example.com` DNS 超时。原始源码复现了完全相同的六个末级失败场景。最终全量复测仅在测试进程中设置 `GODEBUG=netdns=go` 后通过，没有修改测试、断言、系统 DNS 或产品超时。既有 SIMD 和外部 LDAP/OpenID/权限插件跳过仍属于明确的验收边界。旧 etcd 套件使用 `_MINIO_ETCD_TEST_SERVER`，版本测试夹具使用 `SILO_TEST_IAM_REVOCATION_ETCD`；仅启动 etcd，并不意味着每组测试都收到了它所需的配置。

验证过程中还修正了两个夹具问题。KES SDK 可能执行两次最长 999 ms、不能被取消打断的退避休眠；原来的 2 秒测试保护窗口没有覆盖这两次休眠加上 300 ms 请求期限。保护窗口改为有限的 3 秒，同时严格保留“不得新增解密”的断言。真实 32 秒实验还要求 KES 夹具响应合法的周期性 `DescribeKey` 请求。补全夹具后，重新执行了正式与对抗性定向测试，以及三个长耗时 etcd 场景，均通过。

持久化的回归入口为 [`iam-policy-reload_test.go`](https://github.com/pgsty/silo/blob/1b5477f3df87924712ad8dc580c8f8eac63eda2d/cmd/iam-policy-reload_test.go)、[`iam-policy-refresh_test.go`](https://github.com/pgsty/silo/blob/1b5477f3df87924712ad8dc580c8f8eac63eda2d/cmd/iam-policy-refresh_test.go)、[`iam-policy-budget_test.go`](https://github.com/pgsty/silo/blob/1b5477f3df87924712ad8dc580c8f8eac63eda2d/cmd/iam-policy-budget_test.go) 和 [`kms-cancellation_test.go`](https://github.com/pgsty/silo/blob/1b5477f3df87924712ad8dc580c8f8eac63eda2d/cmd/kms-cancellation_test.go)。运行 etcd 用例时应配置可丢弃的独立实例；跳过后端不能证明该后端行为正确。原始调查日志和私有夹具保留在公开源码及文档仓库之外。

## 充分性与保留边界 {#limits}

该修复足以处理已复现的缓存锁连带阻塞、取消信号丢失，以及 R1 的两条期限误用路径。它保留了已检查的并发与兼容性契约，没有扩大为新的调度或统一超时策略。证据支持接受这份源码改动，不能证明系统不存在其他缺陷。

因为保留 `writeMu`，权限管理写入仍可能等待慢策略列表，没有新增固定时限的撤销保证。未设置 deadline、也不主动取消的调用者仍可能等待很久；既有底层预算继续有效，普通缓存命中鉴权可以在策略加载期间通行。

对仍然有效的 SSE-S3 列表请求，原有解密工作仍要执行。本次修复终止取消后的工作，没有让这些解密本身变快，也没有把所有 KMS 方法都改成请求级取消。即使出站请求已收到取消，KES 重试退避仍可能推迟本地返回。

多节点生产行为、托管 CI、发布和部署需要各自验证。正式支持的产品组合是 PGSTY 维护的组件栈；保留 MinIO 接口，不代表对每个未修改的上游组件版本作出保证。

## 留给后续审查的经验 {#lessons}

1. **复用函数时检查它的全部行为。** 想复用锁处理，也可能悄悄引入不合适的期限。
2. **取消必须形成完整调用链。** 检查真正发出去的请求、回退分支、迭代边界与最终缓存发布。
3. **保留合法慢操作的成功能力。** “能取消”的测试不能替代“超过无关后端预算仍应成功”的测试。
4. **用实际加载器验证写入顺序。** 替身如果改变具体后端的选择，可能恰好移除了要验证的竞态。
5. **通过反例证明必要性。** 移除 A、取消传播或 R1 修正，应重新出现对应的可观察失败。
6. **区分产品缺陷和验证缺陷。** 保留失败，与基线对照；补全夹具时不放宽行为断言，不把未执行的场景算作通过。
