**2026 年 10 月 24 日决定：合并修正后的 [PR #257](https://github.com/pgsty/silo/pull/257)（已随 [Server 20261026](/zh/blog/release/silo-20261026/#server-20261026) 发布）。** 提交 [`aafe4f8886`](https://github.com/pgsty/silo/commit/aafe4f8886a060ec698400043bee2f60e22140fd) 修复了 [issue #256](https://github.com/pgsty/silo/issues/256) 报告的多池删除缺陷，并补齐请求开始之后的执行期故障保护。核心不变量是：**先完成其他池的旧副本清理，再删除决定当前读取结果的权威副本。**

Denis Babchuk 报告了该问题并提交了初始补丁。代码评审复现了故障，发现批量删除在通过在线盘数预检查后仍存在执行期故障窗口，随后补充分阶段执行、逐项响应身份保持、部分删除重试以及共享分层对象保护。

## 背景与前置工作 {#background}

SILO 采用按剩余容量加权的选池策略。覆盖写入无版本对象时，新对象可能写入池 B，而池 A 中仍保留旧物理副本。读取路径会跨池选择最新的逻辑对象，因此旧副本平时不可见；但一旦后续删除中途遭遇故障，旧副本就可能重新暴露。

此前合入的多池一致性工作与本次修改的关系如下：

| 已有工作 | 保护范围 | 与本次修改的关系 |
| --- | --- | --- |
| [#178](https://github.com/pgsty/silo/pull/178) | 条件删除和指定版本操作的共享对象锁与跨池协调 | 提供本次复用的锁与协调基础 |
| [#199](https://github.com/pgsty/silo/issues/199)，由 [#207](https://github.com/pgsty/silo/pull/207) 修复 | 条件 `PUT` 针对跨池当前逻辑对象判断条件 | 保留按容量加权的分配策略 |
| [#248](https://github.com/pgsty/silo/pull/248)，随 Server 20261018 合入 | 跨池迁移不得用旧载荷覆盖新副本，也不得丢失删除标记 | 保护 rebalance 与 decommission 迁移路径 |
| [#245](https://github.com/pgsty/silo/pull/245)，已关闭未合并 | 提议覆盖写优先留在原池 | 两轮实验均未达到性能目标；本次修复不依赖覆盖亲和 |

既有协调机制尚未覆盖普通无条件删除与批量删除。共享锁与迁移设计详见[多池对象一致性](/zh/blog/design/multi-pool-object-consistency/)，保留原分配器的评估过程详见[多池覆盖亲和](/zh/blog/design/overwrite-pool-affinity/)。

## 故障现象：删除失败后，已被覆盖的旧值重新可见 {#problem}

假设初始状态如下：

```text
池 A：reports/latest.json = "old"     ModTime = T1
池 B：reports/latest.json = "latest"  ModTime = T2，T2 > T1
GET： "latest"
```

若两个池并行执行删除，池 B 可能先完成删除，池 A 随后返回 I/O 错误。此时单对象 `DELETE` 虽然向客户端返回失败，但最新写入的 `"latest"` 已被物理移除，下一次 `GET` 会读回已被覆盖的 `"old"`。

Issue #256 报告了四类具体表现：

| 操作 | 原有故障行为 |
| --- | --- |
| 普通无版本 `DELETE` | 删除最新副本后返回失败，旧池中的旧值重新可见 |
| 批量 `DeleteObjects` | 某池删除成功掩盖了另一池的删除失败 |
| 批量显式版本删除 | 指定版本仍残留在另一池，却向客户端返回成功 |
| 版本化单个 `DELETE` | 在不满足写 quorum 的持有池尝试创建删除标记，未切换到另一可读可写的持有池 |

运行作者提交的 11 个回归子测试：基线 `main` 有 10 项失败，初始 PR 全部通过。不过，代码评审进一步发现批量删除在通过事前检查后仍存在执行期故障窗口。

### 为什么事前检查不够 {#preflight}

初始补丁在批量删除开始前检查目标纠删集是否有足够的在线磁盘，能够提前拦截已知的离线 quorum 缺失，但无法应对预检查通过后在元数据读写或磁盘删除阶段才发生的 I/O 错误。

评审构造了 45 个故障注入场景：预检查时所有磁盘均在线，先放行最新副本所在池完成删除，再在旧副本所在池的 `DeleteVersions` 内注入故障（覆盖模拟 `EIO`、模拟存储断连与真实文件权限错误，遍历两池和三池下权威副本的每个位置，以及无版本、显式 `null` 与 UUID 版本对象）：

- **基线 `main`（[`000e653038`](https://github.com/pgsty/silo/commit/000e6530386433ff3800f9e0b2d01754ce159c48)）**：在全部 45 个场景中吞掉了逐项删除错误。
- **初始 PR（[`a30270d9ba`](https://github.com/pgsty/silo/commit/a30270d9ba5bc6a5b9f47aa43850465a9b6a5e84)）**：能返回错误，但在全部 30 个无版本与显式 `null` 场景中删掉了最新副本，导致旧值暴露；15 个 UUID 场景因同版本副本内容相同且仍有副本保留，未丢失最新值。

评审同时发现了另一处响应构造缺陷：提前失败的 `DeletedObject` 遗漏了 `ReplicationState`，而 HTTP handler 需要依赖该字段还原原始请求项身份。当签名批量请求包含两个受阻的复制版本清除项时，响应会错误地拆成一个错误项和一个空的删除成功项。仅保留 key 和版本 ID 不足以保证错误项准确对应。

## 删除一致性契约 {#contract}

修复在既有共享对象写锁下，逐项维护以下执行顺序：

1. 解析本次操作指定的对象或版本，确定其权威副本所在池。
2. 先完成所有非权威池的旧副本清理（阶段 0），再尝试删除权威副本（阶段 1）。
3. 若非权威池清理失败，立即向对应的请求项返回错误，且不触碰该项的权威副本。
4. 同一批次中互不相关的其他对象正常完成删除。

各边界行为说明如下：

- **非跨项事务回滚**：若某对象在三个池中都有副本，阶段 0 可能先删掉其中一份旧副本，随后在清理第二份旧副本时失败。此时阶段 1 不会执行，健康的权威副本仍然完好；同一批次中已成功的其他对象不会回滚。
- **权威副本自身的执行期错误**：当阶段 0 全部成功、进入阶段 1 删除权威副本时，若底层磁盘在阶段 1 部分写入后报错，调用方应在存储恢复后检查对象状态并重试。两阶段顺序解决的核心问题是**绝不在已知其他池清理失败的情况下提前删掉权威副本**。
- **显式历史版本删除**：显式指定 `versionId` 删除某个历史版本或删除标记后，更早的保留版本成为当前版本，这属于正常的 S3 版本控制语义。

## 最终实现 {#implementation}

### 单个对象删除 {#single-delete}

普通无版本删除按先旧后新的顺序依次清理各池副本，遇到错误立即停止。条件删除与显式版本删除继续走已有的 `deleteObjectReconciled`。若选中的无版本对象已完成分层（tier）迁移，同样进入 `deleteObjectReconciled`，防止本地清理破坏共享的远端分层引用。

普通单对象创建删除标记时，若多个池持有该对象，协调层会跳过已知不满足删除 quorum 的池，优先选择通过检查的可读持有池写入删除标记。

### 批量数据删除分成两个阶段 {#bulk-delete}

新增的 [`deleteObjectsReconciled`](https://github.com/pgsty/silo/blob/aafe4f8886a060ec698400043bee2f60e22140fd/cmd/erasure-server-pool-consistency.go#L541) 直接复用既有命名空间写锁和 `objectPoolInfos` 解析器，不引入新的锁域。

对象元数据查询并发上限为 32。每项查询读取所有池中的指定版本并按 `ModTime` 排序；时间戳完全相同时以较小的池索引决胜，与读取路径保持一致。不可读元数据直接作为错误处理，绝不视为“该池无此对象”。

```text
持有本批次所有不同 key 的共享写锁
解析每项对象的权威池

阶段 0：批量清理所有非权威池
        将错误记回原始请求项

阶段 1：仅删除阶段 0 清理成功的那些项的权威副本

数据／版本清理之后，再执行删除标记创建
释放锁
```

**每个阶段内部仍跨池并行执行**，继续调用现有的纠删集与磁盘层批量接口。由于同一批次内不同对象的权威副本可能分布在不同存储池，固定全局池顺序无法满足要求，必须按每项各自的权威池划分阶段 0 与阶段 1。

阶段 0 同样包含查询时报告对象不存在的非权威池：读 quorum 看到“不存在”并不能证明某块暂时离线的磁盘上没有残留旧物理副本。若该池无法完成删除，对应请求项会保守返回错误。

所有结果从一开始就完整保留原始 key、版本 ID 和 `ReplicationState`，过滤与重新分批均通过显式下标映射还原请求顺序。在线磁盘预检查继续用于提前拒绝已知的 quorum 缺失，运行期安全性则由两阶段顺序保障。

### 版本配置与删除标记顺序 {#markers}

批量入口沿用底层版本判断规则，区分物理删除与删除标记创建：

| 请求 | 执行动作 |
| --- | --- |
| 显式 `versionId=null` 或 UUID | 物理删除指定版本；多池批量请求执行两阶段清理 |
| 无版本 ID，普通无版本 key | 两阶段物理删除对象数据 |
| 无版本 ID，已启用版本控制 | 创建删除标记，保留历史版本 |
| 无版本 ID，已暂停版本控制 | 创建或替换 `null` 删除标记 |
| 配置了前缀级版本规则 | 对当前 key 计算 `PrefixEnabledFn`，并结合暂停状态判断 |

物理删除先于删除标记创建执行，从而保证同一批次内先显式清除 `null` 版本、再为同一 key 创建新标记时的先后顺序。纯标记批次继续走既有路径（降级场景下的已知边界见下文[兼容性、重试与运行边界](#limits)）。

### 部分磁盘清理后的重试 {#quorum-retry}

当某池仅部分磁盘完成了版本删除、其余磁盘失败时，客户端发起重试会遇到第二类问题：一部分磁盘返回“删除成功”，已删过该版本的磁盘则返回“文件或版本不存在”。若将两类响应分开计票，两边都可能达不到 quorum。

[`erasureObjects.DeleteObjects`](https://github.com/pgsty/silo/blob/aafe4f8886a060ec698400043bee2f60e22140fd/cmd/erasure-object.go#L1894) 的修正**仅针对纯物理删除**将成功移除与 `errFileNotFound` / `errFileVersionNotFound` 合并计入删除 quorum（未知 I/O 错误不计入）。对于创建删除标记或更新复制状态的操作，仍要求实际写入成功达到 quorum，避免把“目标不存在”误判为新标记或元数据状态已落盘。

单版本与批量删除路径（含此处的删除标记写入）的 quorum 为 `floor(N/2) + 1`（`N` 为纠删集磁盘数）。

### 共享分层对象 {#tier}

不同池的物理副本可能指向同一个远端分层对象（包括某份副本已临时恢复到本地的情况）。清理非权威本地副本时，只要保留的权威副本仍依赖该远端对象，就不能将其排入远端垃圾回收。

因此，批量请求中包含已完成分层迁移副本的项会转入既有的逐对象协调路径，完整保留 `SkipFreeVersion`、复制状态与前缀版本选项，并按对象串行执行（同时避免同一批次内的重复项并发改写元数据）。普通本地对象继续走两阶段批量路径。新增回归测试覆盖了共享与独立远端引用、已恢复副本、权威副本删除前失败以及显式 `SkipFreeVersion` 请求。

## 性能：实测删除代价 {#performance}

性能基准直接对比基线 `000e653038` 与最终实现 `a2073d2514`（与合并后的 `main` 源码一致）。

### 测量方法 {#performance-method}

- **硬件环境**：Apple M5 Max（18 物理核心、128 GiB 内存），单块 8 TB Apple SSD（APFS，测试时空间使用率约 95%，所有逻辑目录盘共享该物理 SSD）。
- **配置参数**：每池 4 个目录盘（EC 2+2），4 KiB 对象，8 个并发 worker，`GOMAXPROCS=8`，对象层直接调用（不含 HTTP、鉴权与跨节点 RPC）。
- **测试矩阵**：5 种“池数／副本数”布局（此处的“副本”指一个逻辑对象在不同池中的物理副本数，而非纠删码分片），分别测试单对象 `DELETE`（每轮 1,024 次请求）与每批 64 项的批量删除（每轮 64 次请求、共 4,096 个对象）。
- **采样方式**：每种布局和操作执行 3 对交替运行（基线→修复版、修复版→基线、基线→修复版），每轮重建相同初始布局（准备与清理不计入耗时）。共采集 60 个运行样本、30,720 次单删请求、1,920 次批删请求，累计删除 153,600 个逻辑对象，零请求错误。

### 代价来自哪里 {#performance-cost}

单对象删除需要按先旧后新的顺序串行清理各池副本；批量删除则增加了跨池元数据解析以及阶段 0 到阶段 1 的先后等待（阶段内部仍保持跨池并行与磁盘批处理）。对于批次大小 $B$、池数 $P$、每纠删集磁盘数 $N$，元数据解析需读取 $B \times P$ 个池级对象状态，在线盘预检查至多检查 $B \times P \times N$ 个磁盘状态。由于共享 key 写锁贯穿上述流程，额外耗时也会相应延后针对同一 key 的并发写入。为守住删除失败不丢最新副本的一致性底线，这一多池删除开销是必要且可接受的。

## 兼容性、重试与运行边界 {#limits}

- **错误码与客户端重试**：单对象删除的写 quorum 失败通常返回 HTTP 503；批量 `DeleteObjects` 则在 HTTP 200 响应体内逐项返回 `SlowDownWrite` 等错误码。实测 S3 SDK 在 `MaxRetries=4` 下收到包含逐项 `SlowDownWrite` 的 HTTP 200 响应时不会自动重发整批请求，`mcli rm` 则会直接报告失败项。调用方必须解析批量响应中的错误列表，在存储恢复后携带原 `versionId` 重试失败项。
- **并发与请求取消**：既有共享对象写锁将多池删除与跨池写入串行化。HTTP 批量删除 handler 使用脱离客户端连接的后台 context，客户端中途断连不会中止已开始的批次。
- **暂停版本桶的降级批量标记边界**：补充测试记录了一处在基线 `main` 中既有的边界行为：在两池和三池布局下，仅含 UUID 历史版本的暂停版本桶在磁盘降级期间执行批量删除标记创建，待磁盘恢复后显式清除 `null` 标记仍可能返回 quorum 错误（一次运行暴露出保留的 UUID 历史版本，另一次运行保留了删除标记）。本次修复未改动纯标记批量路径的这一既有行为。
- **Object Lock 与条件删除**：Object Lock 与保留期权限检查保持不变；批量 XML `DeleteObjects` 的 ETag 条件仍不受支持，详见[条件 DELETE](/zh/blog/design/conditional-delete/)。
- **升级与回退**：本次修改不涉及 S3 参数、RPC 协议、磁盘格式、外部依赖、选池分配规则或配置开关变更。混合版本滚动升级期间，尚未升级的协调节点仍按旧逻辑处理其接收的删除请求；回退旧版本不会恢复此前已丢失的副本。

## 备选方案取舍 {#alternatives}

| 备选方案 | 不采纳原因 |
| --- | --- |
| 仅汇总各池错误 | 只能修复“删除失败却报成功”，无法挽回已被提前删掉的最新权威副本 |
| 仅做在线磁盘预检查 | 无法拦截预检查通过后在元数据读写或删除执行阶段才发生的磁盘 I/O 错误 |
| 按固定全局池顺序删除 | 同一批次内不同对象的权威副本可能位于不同存储池，固定池顺序无法兼顾 |
| 所有批量删除全部改为逐对象串行 | 不必要地放弃了普通本地对象的纠删集与磁盘层批处理吞吐；当前仅对含分层引用的对象走逐对象协调路径 |
| 依赖覆盖亲和（#245） | 覆盖亲和会带来常规小对象写入回退，且仍需处理存量跨池副本、迁移副本与中断清理，无法替代删除阶段的顺序保护 |
| 引入跨池回滚事务或配置开关 | 逐项两阶段清理已能保住权威副本，无需引入复杂的分布式回滚状态机或额外开关 |
