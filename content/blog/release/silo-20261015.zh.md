## 对象锁修复 {#object-lock}

- **SN-2026-015 — 保留期授权：** 每个 `PutObjectRetention` 请求都必须获得 `s3:PutObjectRetention` 授权，在读取对象状态前使用请求体条件键求值。缩短、清除未到期 GOVERNANCE 保留期，或改变其模式，还必须同时具备明确的 bypass 请求头与 `s3:BypassGovernanceRetention` 权限。bypass 授权不能覆盖 retention Deny。清除保留期按剩余零天求值，远期日期计算不再饱和。
- **SN-2026-016 — 保护已有版本：** 客户端指定写入版本 ID 必须具备复制信任。目录 `null` 版本与持久化分片目标在实际覆写前、持有目标写锁时复查，覆盖升级前创建或从旧暂存状态恢复的分片上传。已有 GOVERNANCE、COMPLIANCE 与 Legal Hold 保护在实际写入时生效。锁状态读取失败即拒绝操作。
- **发行前置门禁：** [PR #237](https://github.com/pgsty/silo/pull/237) 让发行工作流复用现有 Object Lock race 回归，测试失败会阻止发布制品。回归覆盖慢请求体目录覆写、预检读取失败、旧分片完成覆写 COMPLIANCE，以及恢复上传 UUID 碰撞。

影响行为见[安全公告](/zh/blog/security/20260926-governance-retention-bypass/)，回归边界与设计取舍见[修复设计](/zh/blog/design/governance-retention-bypass-repair/)。

## 升级要求 {#upgrade}

1. 升级全部 Server 进程，以及所有接受 S3 写入的复制站点。已修复站点不会重新授权未修复对端已经接受的保留期变更；混合版本部署仍通过旧写入节点暴露风险。
2. 检查仅授权 bypass、未授权 `s3:PutObjectRetention`，或依赖 bypass 绕过 retention 条件的策略。此类请求现在返回 `403 AccessDenied`；持有基础权限时仍可保持或延长 GOVERNANCE 保留期。
3. 普通 S3 写入不能指定目标 `versionId`，root 签名请求也一样。请使用正常的新版本写入。可信复制仍保留版本 ID；`mcli batch replicate` 写入 SILO 时，目标凭据需具备 `s3:ReplicateObject`。
4. 已锁定的目录对象与已有分片目标不能被覆写。若锁元数据不可读，请先恢复存储健康再重试；读取失败不能作为放行覆写的依据。
5. 排查升级前的审计记录中是否存在意外保留期变更，并核对此前可能受影响的数据。修复阻止新的绕过，不会撤销已接受的变更。从 20260916 之前的版本升级时，还需遵循[九月版升级要求](/zh/blog/release/silo-20260916/#upgrade)。
