## Object Lock repairs {#object-lock}

- **SN-2026-015 — Retention authorization ([#234](https://github.com/pgsty/silo/pull/234))**: every `PutObjectRetention` request requires `s3:PutObjectRetention`, evaluated with request-body Object Lock condition keys before reading object state. Shortening, clearing, or changing the mode of active `GOVERNANCE` retention additionally requires the explicit bypass header and `s3:BypassGovernanceRetention` (which does not override a `Deny` on `s3:PutObjectRetention`). Clearing retention evaluates remaining days as `0`, and distant future dates no longer saturate duration arithmetic.
- **SN-2026-016 — Protected version writes ([#235](https://github.com/pgsty/silo/pull/235))**: caller-selected write `versionId` parameters require trusted replication credentials (`s3:ReplicateObject`). Directory `null` versions and persisted multipart targets are checked under the destination write lock before overwrite (including uploads initiated before upgrading or recovered from legacy staging state), enforcing active `GOVERNANCE`, `COMPLIANCE`, and legal-hold protections; unreadable lock metadata fails closed.
- **Release gate ([#237](https://github.com/pgsty/silo/pull/237))**: the release workflow runs the Object Lock race regression suite as a build prerequisite, covering slow-body directory overwrites, preflight read failures, legacy multipart completions against `COMPLIANCE`, and recovered-upload UUID collisions.

See the [security advisory](/blog/security/20260926-governance-retention-bypass/) and [repair design](/blog/design/governance-retention-bypass-repair/) for full details.

## Upgrade requirements {#upgrade}

1. **Upgrade all writers and replication peers**: upgrade every Server node and all replication sites accepting S3 writes so unpatched peers cannot accept unauthorized retention changes or in-place overwrites.
2. **Review retention policies**: policies granting `s3:BypassGovernanceRetention` without `s3:PutObjectRetention`, or relying on bypass to evade retention condition keys, now receive `403 AccessDenied`.
3. **Caller-selected `versionId` restriction**: ordinary S3 writes (including root-signed requests) cannot specify a target `versionId`; trusted replication preserves version IDs, and `mcli batch replicate` into SILO requires `s3:ReplicateObject` on the destination credentials.
4. **Fail-closed lock checks**: locked directory objects and locked multipart targets cannot be overwritten; if lock metadata is unreadable, restore drive health before retrying.
5. **Audit historical state**: review prior audit logs for unexpected retention changes before the upgrade (when upgrading from releases prior to 20260916, also follow the [September upgrade requirements](/blog/release/silo-20260916/#upgrade)).
