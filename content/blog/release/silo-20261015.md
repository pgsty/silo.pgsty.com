## Object Lock repairs {#object-lock}

- **SN-2026-015 — retention authorization:** every `PutObjectRetention` request requires `s3:PutObjectRetention`, evaluated with request-body condition keys before reading object state. Shortening or removing active GOVERNANCE retention, or changing its mode additionally requires the explicit bypass header and `s3:BypassGovernanceRetention`. A bypass grant no longer overrides a retention Deny. Removal evaluates remaining retention as zero days; distant future dates no longer saturate the calculation.
- **SN-2026-016 — protected version writes:** caller-selected write version IDs require trusted replication. Directory `null` versions and persisted multipart targets are checked under the destination write lock before overwrite, including uploads started before upgrading or recovered from older staging state. Existing GOVERNANCE, COMPLIANCE and legal-hold protection applies at the actual write. Lock-state read failures reject the operation.
- **Release prerequisite:** [PR #237](https://github.com/pgsty/silo/pull/237) makes the release workflow reuse the existing Object Lock race regression suite. A failed regression blocks artifact publication. The suite includes slow-body directory overwrites, preflight read failures, legacy multipart completion against COMPLIANCE and recovered-upload UUID collisions.

See the [security advisory](/blog/security/20260926-governance-retention-bypass/) for affected behavior and the [repair design](/blog/design/governance-retention-bypass-repair/) for regression boundaries and trade-offs.

## Upgrade requirements {#upgrade}

1. Upgrade every Server process and all replication sites that accept S3 writes. A fixed site does not reauthorize a retention change already accepted by an unpatched peer. Mixed deployments remain exposed through their old writers.
2. Review policies that used bypass without `s3:PutObjectRetention`, or relied on bypass to evade retention conditions. They now fail with `403 AccessDenied`. Keeping or extending GOVERNANCE with the base permission remains supported.
3. Ordinary S3 writes cannot choose a target `versionId`, including requests signed by root. Use normal version-creating writes. Trusted replication retains version IDs; `mcli batch replicate` to SILO requires `s3:ReplicateObject` on the target credentials.
4. Locked directory objects and existing locked multipart targets cannot be overwritten. If lock metadata cannot be read, restore storage health before retrying; a read failure does not authorize an overwrite.
5. Review prior audit records for unexpected retention changes and check data affected before the upgrade. The fix prevents new bypasses; it does not undo accepted changes. When upgrading from releases before 20260916, also follow the [September upgrade requirements](/blog/release/silo-20260916/#upgrade).
