## Object Lock and IAM security {#security}

**SN-2026-015 / SN-2026-016 — Object Lock.** [#234](https://github.com/pgsty/silo/pull/234) and [#235](https://github.com/pgsty/silo/pull/235) repair retention authorization and in-place overwrites. Every retention update requires `s3:PutObjectRetention`, evaluated with the request's Object Lock condition keys before object lookup. Weakening active GOVERNANCE also requires the bypass header and `s3:BypassGovernanceRetention`; neither replaces the base permission. Removing retention evaluates remaining days as zero. COMPLIANCE cannot be shortened or changed while active.

Caller-selected write version IDs require trusted replication. Directory `null` versions and persisted multipart targets are checked under the object write lock, and unreadable retention state fails closed. Existing legal holds remain effective. These are Server repairs: updating a client or standalone Console does not protect an old Server. Upgrade all writers and every replication site accepting S3 requests. See the [advisory](/blog/security/20260926-governance-retention-bypass/) and [repair design](/blog/design/governance-retention-bypass-repair/).

**SN-2026-017 — Admin credential authorization.** [#242](https://github.com/pgsty/silo/pull/242) makes self inspection and cleanup respect explicit denies, session restrictions and external-plugin decisions. Under built-in authorization, restricted session credentials cannot create or update broader service accounts, and non-root administrators cannot mutate root's derived credentials. Empty-policy inheritance and cleanup of damaged non-root keys remain supported. The [`995439260`](https://github.com/pgsty/silo/commit/9954392605827b213877c45262c741e638598dd8) follow-up normalizes bulk self-listing aliases to the parent and preserves self inspection for ordinary users with no policy attachment. No new Admin action or IAM storage migration is introduced. See the [security note](/blog/security/20261018-release-hardening/#sn-2026-017) and [authorization contract](/blog/design/iam-admin-authorization/).

## Scoped STS revocation {#sts-revocation}

[`0cd388c66`](https://github.com/pgsty/silo/commit/0cd388c666f8211f552604ae73448a066e9c25ce) makes `RevokeTokens` enumerate durable STS identities as well as cached ones. A node that missed token issuance can now revoke the selected tokens. Each committed token tombstone is sent to sibling nodes and replication peers even if another token fails to save; offline peers recover it through existing IAM deletion healing. Object-backed and etcd-backed cache refreshes also evict revoked tokens after missed notifications or watches.

The scope remains the requested **parent and optional token type**, using the request cluster's snapshot before the operation cutoff. Tokens issued at an isolated site and never replicated into that cluster are outside the snapshot. New token keys, unrelated users and parent policies are preserved. Revocation is eventual across a partition; it is not an instantaneous global barrier. Keep all participating servers on the coordinated version and retain revocation history. Durable enumeration adds work to the administrative revoke path, not a network query to each authentication. See the [STS design and cost](/blog/design/iam-revocations/#scoped-sts-20261018).

## Rebalance and decommission {#pool-migration}

[`60c7179dd`](https://github.com/pgsty/silo/commit/60c7179ddbfcbd41a1fe67707230f5b360a43020), incorporating [#248](https://github.com/pgsty/silo/pull/248), and [`1748f62c7`](https://github.com/pgsty/silo/commit/1748f62c7ec4f2e9afcdce276193ad401719b951) prevent an older moved copy from overwriting the current copy in another pool. The migration rechecks the source version under the shared object lock, preserves null and UUID delete markers, and cleans only confirmed moved versions instead of deleting an entire source prefix. Concurrent writes, deletes or destination changes can stop cleanup for retry.

These repairs apply to rebalance/decommission data movement, including multipart completion and tiered-object metadata. They do not reconstruct content, tags or markers lost in an earlier migration, or resolve the separate cross-site marker problem in #217. Extra metadata reads and per-version cleanup increase migration cost with pool count and version history. Review the [migration design](/blog/design/multi-pool-object-consistency/#migration-20261018) and verify versions, tags and deletion state before retiring a pool.

## Ordinary object listings {#listing}

[#239](https://github.com/pgsty/silo/pull/239), incorporating the original #221 work, addresses readable keys omitted by successful `ListObjects` / `ListObjectsV2` responses under eligible metadata disagreements. The pool merger confirms uncertain same-name groups under the relevant object read locks. It returns current readable metadata, omits confirmed absence, or returns an error such as `503 SlowDownRead` when it cannot establish either. A failed pagination producer remains a failed scan; clients must consume every page and treat a failed page as an incomplete inventory.

Ordinary resolved entries keep their fast path. Recovery is limited to eligible latest-object groups; it does not widen full version-history resolution, lower quorum, add persistent metadata, or promise a snapshot across pages. Cancellation interrupts lock backoff, and identified recovery conflicts get a bounded short wait. The [`3dd53eb81`](https://github.com/pgsty/silo/commit/3dd53eb81) and [`2080b3d03`](https://github.com/pgsty/silo/commit/2080b3d03) follow-ups preserve directory/common-prefix entries when a colliding object is confirmed absent, including mixed entry ordering.

The [design and cost record](/blog/design/listing-recovery-lock-cost/) retains the measured limits: the strict target of no more than 5% p95 degradation was **not confirmed** by that comparison. Earlier source acceptance is not final-artifact or production performance acceptance. #218 is closed by the source repair; that does not establish that every LIST omission or concurrent inventory problem is solved.

## Multipart uploads and cleanup {#multipart}

**The release does not enable persistent multipart enumeration.** The October 17 default-scan implementation in #243 was withdrawn by [`4733e1423`](https://github.com/pgsty/silo/commit/4733e1423cfe703951f52ff9cbd286df2cf9d79d). Public `ListMultipartUploads` uses the node-local cache for an empty prefix and an exact-key lookup for a nonempty prefix. Restart or a different serving node can omit uploads; true prefix filtering, grouping and cache pagination remain incomplete. [#79](https://github.com/pgsty/silo/issues/79) remains open.

Compared with 20260916, **users who enabled `MINIO_API_MULTIPART_LISTING=strict` lose durable listing and strict cancellation**. The variable is ignored with a startup warning; the obsolete shared `api multipart_listing` key is tolerated. There is no replacement switch. Default read-quorum, best-effort Abort and first-matching-pool behavior are retained. HTTP 204 does not prove every physical copy was removed, and delayed creation writes can still restore an upload.

Identity metadata, UploadID path validation, wrong-target checks and successful-abort cache/peer notification remain. The read-only `multipart-preflight` Admin diagnostic still requires `admin:StorageInfo` and reports `mode=legacy`. Its scan-entry, time and admission limits apply to explicit diagnostics, not public listing or startup. It is not a complete inventory or bulk-cleanup guarantee. See the [decision, migration impact and capacity limits](/blog/design/list-multipart-uploads/#implementation) and [setting reference](/reference/minio-server/settings/core/#multipart-listing).

Cleanup receives two independent repairs:

- [#236](https://github.com/pgsty/silo/pull/236) parses native upload-directory timestamps before the Base64 compatibility fallback, avoiding unnecessary metadata reads. Unknown historical names still fall back to metadata.
- [`0f9199e0c`](https://github.com/pgsty/silo/commit/0f9199e0c3e768bb7699bd640ddad3d6b5d0628b) removes empty upload-parent directories without waiting for their newly refreshed modification time to expire again. Nonempty parents, active uploads and unreadable records remain protected.

The default stale-upload expiry is still **24 hours**, with cleanup checks every **6 hours**. Restarting is not cleanup, and an empty listing is not evidence of reclaimed disk space.

## Upgrade and rollback {#upgrade}

1. Record the actual installed versions and pin the accepted binaries or image digests. Back up complete IAM storage, configuration and required encryption material. Follow [migration](/compatibility/migration/) and [IAM recovery](/operations/replication/iam-upgrade/); a live IAM export omits revocation history.
2. Coordinate all Server processes, writers and replication sites. Do not mix old/new binaries against the same IAM backend or treat a rolling downgrade as supported. Replacing the standalone UI or client does not replace the embedded Server components.
3. Test retention updates, legal holds, caller-selected write IDs, service-account creation/update, explicit self denies and root administration with the credentials your automation actually uses. Reissue previously unusable expiring keys through an authorized parent instead of erasing stored policy claims.
4. If strict multipart listing was enabled, remove that operational dependency before upgrading. Preserve known bucket/key/UploadID tuples for completion or cancellation. Do not use the public list to certify full discovery, full cancellation or reclaimed space.
5. Verify ordinary and paginated LIST, PUT/completion retry handling, OIDC/JWKS, TLS-inspecting outbound paths, replication and scanner progress. Errors must not be converted to a successful empty inventory. See the [TLS guide](/blog/design/go127-tls-oidc-discovery/).
6. Audit existing retention, credentials, replicas and pending delete markers independently. The upgrade does not restore overwritten versions, lost tags, earlier retention or already-lost revocation history. Returning to 20260916 reintroduces the October security defects.

## Remaining limits and delivery evidence {#delivery}

Multi-site delete-marker late creation and post-crash minority residue remain tracked in [#217](https://github.com/pgsty/silo/issues/217). Complete, scalable multipart enumeration and creation fencing remain open in #79. LIST recovery preserves its eligibility limits and version-history contract. Neither this release nor its documentation promises snapshot inventories or new on-disk recovery guarantees.

The signed tag and all 36 finalized release assets identify `0cd388c666f8211f552604ae73448a066e9c25ce`. The October 18 local acceptance record verified their digests, six archive stamps and six package payloads, 34 build attestations, two Sigstore checksum signatures, two signed RPMs and 12 SBOMs. The exact source passed [Go CI](https://github.com/pgsty/silo/actions/runs/39136984202), [VulnCheck](https://github.com/pgsty/silo/actions/runs/39136984236), [Release](https://github.com/pgsty/silo/actions/runs/39137110821) and [package finalization](https://github.com/pgsty/silo/actions/runs/39138591714).

Local tests used the binaries downloaded while the release was still Draft. They covered native Darwin and Linux S3/IAM/STS/Object Lock, LDAP/OIDC, upgrade from 20260916, bucket and site replication, three-site recovery with Console, three-site and four-process shared-cluster STS revocation, and four real migration cases (2/3 pools × rebalance/decommission). Eight processes in two pools completed 2,896 rolling-restart load scans and 1,270 fault-recovery load scans without missing keys, duplicates or corrupted reads. Three Linux package lifecycle cases and eight local container variants also passed.

**The local candidate acceptance is complete, and the release is now public.** The processes and Docker VM shared one physical host; amd64 containers ran under emulation. Windows and Darwin amd64 artifacts received static checks, not runtime acceptance. Encryption tests used a local test KMS key; they do not certify real cloud IAM/KMS or the final Server with external KES. Independent physical failure domains, production performance SLOs and real systemd boot were not established. Fault windows included request errors and delays; successful content checks do not mean uninterrupted service or prove a p95 regression below 5%.

Historical [20261015 artifact tests](/blog/release/silo-20261015/#acceptance) retain their own source and environment boundaries. Anonymous release downloads and Docker Hub publication are verified below; package-repository mirrors and deployment to a particular production environment remain separate delivery steps. KES, Console, mcli and pkg have their own published release records.
