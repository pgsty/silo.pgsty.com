## Object Lock and IAM security {#security}

**SN-2026-015 / SN-2026-016 — Object Lock retention authorization and in-place overwrite protection.** [#234](https://github.com/pgsty/silo/pull/234) and [#235](https://github.com/pgsty/silo/pull/235) repair retention authorization and in-place overwrites:

- Every `PutObjectRetention` request evaluates `s3:PutObjectRetention` with the request's Object Lock condition keys before looking up the target object. Shortening, clearing, or changing the mode of an active `GOVERNANCE` retention additionally requires both `x-amz-bypass-governance-retention: true` and `s3:BypassGovernanceRetention` (which supplements rather than replaces `s3:PutObjectRetention`). Clearing retention evaluates remaining retention days as `0`, and active `COMPLIANCE` retention cannot be shortened or changed.
- Caller-selected write `versionId` parameters require trusted replication credentials (`s3:ReplicateObject`). Directory `null` versions and persisted multipart targets are re-verified under the destination write lock, and unreadable retention metadata fails closed while preserving existing legal holds. Upgrade all writing nodes and every replication site accepting S3 requests. See the [security advisory](/blog/security/20260926-governance-retention-bypass/) and [repair design](/blog/design/governance-retention-bypass-repair/).

**SN-2026-017 — Admin credential self-service authorization.** [#242](https://github.com/pgsty/silo/pull/242) ensures credential self-inspection and cleanup respect explicit `Deny` statements, session-policy restrictions (`sessionPolicy`), and external authorization plugin decisions. Under built-in authorization, restricted session credentials cannot create or update service accounts broader than their own scope, and non-root administrators cannot mutate root's derived credentials; unrestricted empty-policy inheritance and cleanup of damaged non-root keys remain supported. Follow-up commit [`995439260`](https://github.com/pgsty/silo/commit/9954392605827b213877c45262c741e638598dd8) normalizes bulk self-listing aliases to the parent identity and preserves self-inspection for ordinary users without attached policies, requiring no new Admin actions or IAM storage migration. See the [security note](/blog/security/20261018-release-hardening/#sn-2026-017) and [authorization contract](/blog/design/iam-admin-authorization/).

## Scoped STS revocation {#sts-revocation}

[`0cd388c66`](https://github.com/pgsty/silo/commit/0cd388c666f8211f552604ae73448a066e9c25ce) updates `RevokeTokens` to enumerate durable STS identity records alongside in-memory caches, allowing nodes that missed an earlier token-issuance notification to revoke matching tokens reliably. Committed token tombstones are broadcast to sibling nodes and site-replication peers even if another token in the batch fails to save, and offline peers converge via IAM deletion healing. Object-backed and etcd-backed cache refreshes also evict revoked tokens after missed notifications or watches.

The revocation scope remains the requested **parent identity and optional token type** across the cluster's snapshot prior to the operation cutoff, leaving newly issued tokens, unrelated users, and parent policies untouched. Durable enumeration adds work only to the administrative revocation path, not to per-request authentication. See the [STS revocation design and cost analysis](/blog/design/iam-revocations/#scoped-sts-20261018).

## Rebalance and pool decommission consistency {#pool-migration}

[`60c7179dd`](https://github.com/pgsty/silo/commit/60c7179ddbfcbd41a1fe67707230f5b360a43020) (incorporating [#248](https://github.com/pgsty/silo/pull/248)) and [`1748f62c7`](https://github.com/pgsty/silo/commit/1748f62c7ec4f2e9afcdce276193ad401719b951) prevent rebalance and pool-decommission workflows from overwriting a newer object copy in another pool with an older migrated copy. Migration re-verifies source versions (including multipart completions and tiered-object metadata) under the shared object lock, preserves `null` and UUID delete markers, and removes only confirmed migrated versions rather than deleting the entire source prefix. Concurrent writes, deletes, or destination changes safely abort cleanup for a later retry.

Before retiring a pool, verify object versions, tags, and delete-marker state as described in [multi-pool object consistency](/blog/design/multi-pool-object-consistency/#migration-20261018) (independent cross-site delete-marker ordering remains tracked in [#217](https://github.com/pgsty/silo/issues/217)).

## Ordinary object listing recovery {#listing}

[#239](https://github.com/pgsty/silo/pull/239) (incorporating the original #221 work and closing #218) fixes an issue where `ListObjects` / `ListObjectsV2` could succeed while omitting readable keys during eligible cross-pool metadata disagreements. The pool merger now re-verifies uncertain same-name entry groups under the corresponding object read locks: it returns current readable metadata, omits confirmed absent keys, or returns an explicit error such as `503 SlowDownRead` when quorum cannot establish either state. A failed pagination producer fails the scan; clients must consume all pages and treat any page error as an incomplete listing.

Resolved entries retain their lock-free fast path. Recovery applies only to eligible latest-object groups without lowering quorum or adding persistent metadata; request cancellation interrupts lock backoff, and identified recovery lock conflicts wait for a single bounded interval. Follow-up commits [`3dd53eb81`](https://github.com/pgsty/silo/commit/3dd53eb81) and [`2080b3d03`](https://github.com/pgsty/silo/commit/2080b3d03) preserve directory and `CommonPrefixes` entries when a colliding object name is confirmed absent. Measured latency and lock-cost benchmarks are documented in [listing recovery lock cost](/blog/design/listing-recovery-lock-cost/).

## Multipart upload listing and cleanup {#multipart}

**Default disk scan rolled back to legacy in-memory listing.** The default disk-scan implementation merged on October 17 (#243) was withdrawn by [`4733e1423`](https://github.com/pgsty/silo/commit/4733e1423cfe703951f52ff9cbd286df2cf9d79d). Public `ListMultipartUploads` uses the node-local in-memory cache when `prefix` is empty and performs an exact-key lookup when `prefix` is nonempty; process restarts or requests routed to different nodes can omit in-flight uploads (scalable persistent enumeration remains tracked in [#79](https://github.com/pgsty/silo/issues/79)).

Compared with 20260916, **`MINIO_API_MULTIPART_LISTING=strict` is retired**: setting the environment variable logs a startup warning and is ignored (the legacy shared `api multipart_listing` config key is likewise tolerated and ignored). However, the 20260916 upload-creation identity metadata, `uploadId` path validation, abort target matching, and post-abort cache/peer notifications remain active. The read-only `multipart-preflight` Admin diagnostic still requires `admin:StorageInfo` and reports `mode=legacy`, applying its entry, timeout, and concurrency budgets strictly to explicit diagnostic calls. See the [multipart listing design, rollback rationale, and capacity benchmarks](/blog/design/list-multipart-uploads/#implementation) and the [configuration reference](/reference/minio-server/settings/core/#multipart-listing).

Background stale-upload cleanup (default **24-hour** expiry checked every **6 hours**) includes two repairs:

- [#236](https://github.com/pgsty/silo/pull/236) parses native upload-directory timestamps before falling back to Base64 decoding, avoiding unnecessary disk metadata reads.
- [`0f9199e0c`](https://github.com/pgsty/silo/commit/0f9199e0c3e768bb7699bd640ddad3d6b5d0628b) removes empty upload-parent directories immediately after deleting expired child upload directories, rather than waiting another 24-hour cycle after child deletion updates the parent's `mtime` (nonempty parents and active uploads remain protected).

## Upgrade and rollback checklist {#upgrade}

1. **Back up state and pin artifacts**: record your installed versions and pin verified binary or image digests. Follow the [migration guide](/compatibility/migration/) and [IAM recovery procedure](/operations/replication/iam-upgrade/) to back up complete IAM storage, configuration, and encryption keys (standard live IAM exports omit revocation tombstones).
2. **Coordinate cluster cutover**: upgrade all Server nodes and replication sites together; do not mix old and new binaries against the same IAM backend or perform rolling cross-version downgrades.
3. **Verify Object Lock and service-account policies**: test retention updates, legal holds, service-account creation/updates, explicit self `Deny` rules, and root credential management with the exact credentials used by your automation. Reissue previously damaged expiring keys through an authorized parent identity.
4. **Remove `strict` multipart listing dependencies**: if `MINIO_API_MULTIPART_LISTING=strict` was enabled on 20260916, ensure clients track their own active `bucket/key/UploadID` tuples for completion or cancellation rather than relying on public `ListMultipartUploads` for full discovery.
5. **Check listing, retry handling, and OIDC/TLS paths**: verify ordinary and paginated `LIST`, client retry policies for `503 SlowDownWrite` on PUT/completion, OIDC/JWKS RSA key sizes, and outbound connections across TLS-inspecting middleboxes (see the [Go 1.27 TLS and OIDC guide](/blog/design/go127-tls-oidc-discovery/)).
6. **Rollback considerations**: downgrading to 20260916 reintroduces the October Object Lock and admin credential vulnerabilities, and upgrading does not retroactively restore versions or tags overwritten prior to the upgrade.
