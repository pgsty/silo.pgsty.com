## Object Lock 与 IAM 安全修复 {#security}

**SN-2026-015 / SN-2026-016 — Object Lock 保留期授权与原位覆写防护。** [#234](https://github.com/pgsty/silo/pull/234) 与 [#235](https://github.com/pgsty/silo/pull/235) 修复了保留期修改鉴权与原位覆写漏洞：

- 每次 `PutObjectRetention` 请求在读取目标对象前，都会携带请求中的 Object Lock 条件键校验 `s3:PutObjectRetention`。缩短、清空未到期的 `GOVERNANCE` 保留期或切换其模式时，调用方必须同时提供 `x-amz-bypass-governance-retention: true` 请求头并具备 `s3:BypassGovernanceRetention` 权限（不能替代基础 `s3:PutObjectRetention` 权限）。清空保留期时剩余天数按 `0` 计算；未到期的 `COMPLIANCE` 保留期不允许缩短或更改模式。
- 调用方显式指定写入 `versionId` 时必须具备可信复制身份（`s3:ReplicateObject`）。目录对象的 `null` 版本和已持久化的分片上传目标会在对象写锁内重新校验锁状态；锁状态读取失败时按 fail-closed 拒绝写入，既有 Legal Hold 继续生效。请同步升级集群中所有写入节点及接收 S3 请求的复制站点。详见[安全公告](/zh/blog/security/20260926-governance-retention-bypass/)与[修复设计](/zh/blog/design/governance-retention-bypass-repair/)。

**SN-2026-017 — 管理凭据自助授权边界。** [#242](https://github.com/pgsty/silo/pull/242) 使凭据自查询与清理严格遵守显式 `Deny`、会话策略收窄（`sessionPolicy`）及外部授权插件判定。在内置授权下，受限会话凭据无法创建或更新权限超出自身范围的服务账号，非 root 管理员也无法修改 root 派生的凭据；无限制空策略继承与损坏的非 root 密钥清理保持支持。后续提交 [`995439260`](https://github.com/pgsty/silo/commit/9954392605827b213877c45262c741e638598dd8) 将批量自查询别名归一到父身份，并保留无附加策略普通用户的自查询能力，无需新增 Admin action 或迁移 IAM 存储。详见[安全笔记](/zh/blog/security/20261018-release-hardening/#sn-2026-017)与[授权契约](/zh/blog/design/iam-admin-authorization/)。

## 按范围撤销 STS 令牌 {#sts-revocation}

[`0cd388c66`](https://github.com/pgsty/silo/commit/0cd388c666f8211f552604ae73448a066e9c25ce) 让 `RevokeTokens` 同时枚举持久化 STS 身份记录与节点内存缓存，即使某个节点此前漏掉了令牌签发通知，也能完整撤销目标令牌。即便批次中个别令牌写入墓碑失败，已提交的删除记录仍会广播给同集群节点与站点复制对端；离线站点在恢复后通过既有 IAM 删除自愈补齐。基于对象存储和 etcd 的缓存刷新也会在通知或 watch 遗漏后自动剔除已撤销令牌。

撤销范围仍为请求指定的**父身份及可选令牌类型**（覆盖请求集群在操作截点前的快照，不影响新签发的令牌、无关用户或父身份策略）。持久枚举仅增加管理端撤销命令的开销，不为日常请求鉴权增加网络查询。详见 [STS 撤销设计与成本](/zh/blog/design/iam-revocations/#scoped-sts-20261018)。

## 重平衡与池下线一致性 {#pool-migration}

[`60c7179dd`](https://github.com/pgsty/silo/commit/60c7179ddbfcbd41a1fe67707230f5b360a43020)（含 [#248](https://github.com/pgsty/silo/pull/248)）与 [`1748f62c7`](https://github.com/pgsty/silo/commit/1748f62c7ec4f2e9afcdce276193ad401719b951) 防止 rebalance 或池下线（decommission）搬迁旧副本时覆盖其他存储池中的最新副本。搬迁流程会在共享对象锁内复核源版本（包含分片完成与分层对象元数据），保留 `null` 与 UUID 删除标记，并仅清理已确认搬迁完成的版本，不再粗暴删除整个源前缀。若期间发生并发写入、删除或目标池变化，清理会安全中止并留待重试。

退役旧存储池前，请按[多池对象一致性设计](/zh/blog/design/multi-pool-object-consistency/#migration-20261018)核验对象版本、标签和删除标记状态（跨站点删除标记的独立边界仍由 [#217](https://github.com/pgsty/silo/issues/217) 跟踪）。

## 普通对象列表恢复 {#listing}

[#239](https://github.com/pgsty/silo/pull/239)（含原 #221 工作，关闭 #218）修复了在符合恢复条件的元数据分歧下，`ListObjects` / `ListObjectsV2` 成功返回却遗漏可读对象 key 的问题。多池合并层会在对象读锁内复核存在分歧的同名条目组：返回当前可读元数据、略过已确认不存在的对象，或在无法确认时返回 `503 SlowDownRead` 等明确错误。分页生产者出错会终止整次扫描；客户端应消费所有分页并将任一分页错误视为不完整列表。

常规无分歧条目继续走原有的无锁快速路径。锁内复核仅针对符合条件的最新对象组，不降低读仲裁要求，也不新增持久化元数据；请求取消可随时中断锁重试等待，遇到恢复锁冲突时仅执行一次有界短等待。后续提交 [`3dd53eb81`](https://github.com/pgsty/silo/commit/3dd53eb81) 与 [`2080b3d03`](https://github.com/pgsty/silo/commit/2080b3d03) 确保当同名碰撞对象被确认为不存在时，同名目录或公共前缀（`CommonPrefixes`）仍被完整保留。实测延迟与锁开销见[列表恢复锁成本记录](/zh/blog/design/listing-recovery-lock-cost/)。

## 分片上传列举与清理 {#multipart}

**回退默认磁盘扫描，恢复 Legacy 内存列举。** #243 在 10 月 17 日引入的默认磁盘扫描已由 [`4733e1423`](https://github.com/pgsty/silo/commit/4733e1423cfe703951f52ff9cbd286df2cf9d79d) 撤回。公开 `ListMultipartUploads` 在空 `prefix` 时查询节点本地内存缓存，在非空 `prefix` 时按精确对象 key 查找；进程重启或请求落到其他节点可能遗漏未完成上传（跨池持久化列举仍在 [#79](https://github.com/pgsty/silo/issues/79) 中跟踪）。

与 20260916 相比，**环境变量 `MINIO_API_MULTIPART_LISTING=strict` 已停用**：设置该变量会在启动时输出警告并被忽略（旧共享配置键 `api multipart_listing` 同样被容忍忽略）。但 20260916 引入的上传创建身份元数据、UploadID 路径校验、取消目标匹配检查以及成功取消后的缓存/对端清理通知均得以保留。只读管理诊断接口 `multipart-preflight` 仍要求 `admin:StorageInfo` 权限并返回 `mode=legacy`，其扫描条目数、超时与并发上限仅作用于显式管理诊断。详见[分片列举设计、回退原因与容量基准](/zh/blog/design/list-multipart-uploads/#implementation)及[配置参考](/zh/reference/minio-server/settings/core/#multipart-listing)。

后台过期分片清理（默认 **24 小时**过期、每 **6 小时**巡检一次）包含两项修复：

- [#236](https://github.com/pgsty/silo/pull/236)：优先解析原生上传目录名中的时间戳，再回退尝试 Base64 兼容路径，消除无谓的磁盘元数据读取。
- [`0f9199e0c`](https://github.com/pgsty/silo/commit/0f9199e0c3e768bb7699bd640ddad3d6b5d0628b)：删除过期上传子目录后，立即清理变空的父目录，不再因删除子目录刷新了父目录 `mtime` 而多等一轮 24 小时过期周期（非空父目录与活跃上传不受影响）。

## 升级与回滚要点 {#upgrade}

1. **备份状态与固定制品**：记录当前运行版本并固定目标二进制或镜像 digest；按[迁移指南](/zh/compatibility/migration/)与 [IAM 恢复流程](/zh/operations/replication/iam-upgrade/)完整备份 IAM 存储、配置与加密材料（常规在线 IAM 导出不包含撤销墓碑历史）。
2. **全集群同步切换**：协调升级所有 Server 节点与接收写入的复制站点，切勿在同一 IAM 后端混跑新旧二进制或执行跨版本滚动降级。
3. **核对 Object Lock 与服务账号权限**：使用业务实际凭据验证保留期修改、Legal Hold、服务账号创建/更新、自助操作显式 `Deny` 以及 root 凭据管理。此前因策略格式受损而无法使用的到期密钥，应由授权父身份重新签发。
4. **移除 `strict` 分片列举依赖**：若此前在 20260916 上启用了 `MINIO_API_MULTIPART_LISTING=strict`，升级前请确保客户端自行维护待完成或待取消的 `bucket/key/UploadID`，不要依赖公开列表进行全量发现或空间回收判断。
5. **检查列表、重试与 OIDC/TLS 链路**：验证普通与分页 `LIST`、PUT/分片完成对 `503 SlowDownWrite` 的重试、OIDC/JWKS 密钥长度及经过 TLS 检查设备的出站连接（参见 [Go 1.27 TLS 与 OIDC 指南](/zh/blog/design/go127-tls-oidc-discovery/)）。
6. **回滚风险**：降级回 20260916 会重新暴露本版修复的 Object Lock 与管理凭据授权缺陷，且升级本身不会自动恢复升级前已被覆写的对象版本或丢失的标签。
