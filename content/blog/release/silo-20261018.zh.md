## Object Lock 与 IAM 安全修复 {#security}

**SN-2026-015 / SN-2026-016 — Object Lock。** [#234](https://github.com/pgsty/silo/pull/234) 与 [#235](https://github.com/pgsty/silo/pull/235) 修复保留期授权和原位覆盖。每次保留期修改都必须在读取对象前，带请求中的 Object Lock 条件键校验 `s3:PutObjectRetention`。削弱未到期的 GOVERNANCE 还必须同时提供绕过头并拥有 `s3:BypassGovernanceRetention`；两者均不能替代基本权限。清除保留期时，剩余天数按零计算；未到期的 COMPLIANCE 仍不能缩短或改变模式。

调用者指定写入版本 ID 必须具备可信复制身份。目录 `null` 版本和已持久化的分片目标会在对象写锁内重新检查；无法读取保留状态时拒绝写入，既有合法保留继续生效。这是 Server 修复：更新客户端或独立 Console 不能保护旧 Server。必须升级所有写入节点及接受 S3 请求的复制站点，参见[安全公告](/zh/blog/security/20260926-governance-retention-bypass/)与[修复设计](/zh/blog/design/governance-retention-bypass-repair/)。

**SN-2026-017 — 管理凭据授权。** [#242](https://github.com/pgsty/silo/pull/242) 让自助查询与清理遵守显式 Deny、会话限制和外部授权插件的决定。使用内置授权时，受限会话凭据不能创建或更新权限更宽的服务账户，非 root 管理员不能修改 root 的派生凭据。空策略继承与损坏的非 root 密钥清理仍受支持。后续 [`995439260`](https://github.com/pgsty/silo/commit/9954392605827b213877c45262c741e638598dd8) 将批量自查询的别名统一到父身份，并保留无策略绑定普通用户的自查询能力。没有新增 Admin action 或 IAM 存储迁移。参见[安全笔记](/zh/blog/security/20261018-release-hardening/#sn-2026-017)与[授权契约](/zh/blog/design/iam-admin-authorization/)。

## 按范围撤销 STS 令牌 {#sts-revocation}

[`0cd388c66`](https://github.com/pgsty/silo/commit/0cd388c666f8211f552604ae73448a066e9c25ce) 让 `RevokeTokens` 同时枚举持久 STS 身份与缓存，漏掉签发通知的节点也能撤销选中的令牌。即使其他令牌保存失败，已提交的删除记录仍会通知同集群节点及复制站点；离线站点通过既有 IAM 删除恢复补齐。对象存储与 etcd 的缓存刷新也会在通知或 watch 遗漏后剔除已撤销令牌。

范围仍为请求指定的**父身份及可选令牌类型**，覆盖请求集群在操作截点之前的快照。孤立站点签发、从未复制到本集群的令牌不在快照中。新签发的令牌 key、无关用户和父身份策略保持不变。分区后的撤销是最终收敛，不是瞬时全局屏障。所有参与服务器应协调升级，并保留撤销历史。持久枚举增加的是管理撤销路径的工作量，不会为每次鉴权新增网络查询。参见 [STS 设计与成本](/zh/blog/design/iam-revocations/#scoped-sts-20261018)。

## 重平衡与池下线 {#pool-migration}

[`60c7179dd`](https://github.com/pgsty/silo/commit/60c7179ddbfcbd41a1fe67707230f5b360a43020) 纳入 [#248](https://github.com/pgsty/silo/pull/248)，与 [`1748f62c7`](https://github.com/pgsty/silo/commit/1748f62c7ec4f2e9afcdce276193ad401719b951) 共同防止迁移旧副本覆盖其他池中的当前副本。迁移在共享对象锁内复核源版本，保留 null 与 UUID 删除标记，仅清理确认迁移完成的版本，不再删除整个源前缀。并发写入、删除或目标变化可能中止清理，留待重试。

修复覆盖 rebalance/decommission 数据搬迁，包括分片完成与分层对象元数据；不会重建早先迁移已丢失的内容、标签或删除标记，也不解决 #217 中独立的跨站标记问题。新增元数据读取与逐版本清理会随池数和版本历史增加迁移成本。退役旧池前，应按[迁移设计](/zh/blog/design/multi-pool-object-consistency/#migration-20261018)核验版本、标签和删除状态。

## 普通对象列表 {#listing}

[#239](https://github.com/pgsty/silo/pull/239) 纳入原 #221 工作，修复符合恢复条件的元数据分歧下，`ListObjects` / `ListObjectsV2` 成功返回却遗漏可读 key 的问题。池合并层在相应对象读锁内确认同名条目组：返回当前可读元数据、略过已确认不存在的对象，或在两者均无法确认时返回 `503 SlowDownRead` 等错误。分页生产者失败会保留为整次扫描失败；客户端必须读取所有分页，并把任一分页失败视为清单不完整。

普通已解析条目保留快速路径。恢复仅适用于符合条件的最新对象组，不扩大完整版本历史的解析范围，不降低仲裁，不新增持久元数据，也不保证跨页快照。取消能中断锁重试等待，识别出的恢复锁冲突获得一次有限短等待。后续 [`3dd53eb81`](https://github.com/pgsty/silo/commit/3dd53eb81) 与 [`2080b3d03`](https://github.com/pgsty/silo/commit/2080b3d03) 保证碰撞对象被确认不存在后仍保留目录／公共前缀，包括混合条目顺序。

[设计与成本记录](/zh/blog/design/listing-recovery-lock-cost/)保留实测边界：该次比较**尚未确认** p95 劣化不超过 5% 的严格目标。历史源码验收不等于最终制品或生产性能验收。#218 已由源码修复关闭，但不能据此宣称消除了所有 LIST 遗漏或并发清单问题。

## 分片上传与清理 {#multipart}

**本版不启用持久化分片枚举。** #243 在 10 月 17 日引入的默认扫描已被 [`4733e1423`](https://github.com/pgsty/silo/commit/4733e1423cfe703951f52ff9cbd286df2cf9d79d) 撤回。公开 `ListMultipartUploads` 在空 prefix 时使用节点本地缓存，在非空 prefix 时按精确 key 查询。重启或换节点可能遗漏上传；真正的前缀过滤、分组与缓存分页仍不完整。[#79](https://github.com/pgsty/silo/issues/79) 保持开放。

相较 20260916，**启用过 `MINIO_API_MULTIPART_LISTING=strict` 的用户将失去持久列表与严格取消能力**。该变量会被忽略并产生启动警告；废弃的共享 `api multipart_listing` 键仍被容忍，没有替代开关。默认读仲裁、尽力取消和首个匹配池行为保留。HTTP 204 不证明每个物理副本都已删除，延迟到达的创建写入仍可能使上传重新出现。

身份元数据、UploadID 路径校验、目标匹配检查，以及成功取消后的缓存／节点通知均保留。只读 Admin 诊断 `multipart-preflight` 继续要求 `admin:StorageInfo`，返回 `mode=legacy`。其目录条目、时间和并发预算只约束显式诊断，不约束公开列表或启动，也不保证完整清单或批量清理。参见[决策、迁移影响与容量边界](/zh/blog/design/list-multipart-uploads/#implementation)及[配置参考](/zh/reference/minio-server/settings/core/#multipart-listing)。

清理路径包含两项独立修复：

- [#236](https://github.com/pgsty/silo/pull/236) 先解析原生上传目录时间戳，再尝试 Base64 兼容路径，避免不必要的元数据读取；无法识别的历史名称仍回退读取元数据。
- [`0f9199e0c`](https://github.com/pgsty/silo/commit/0f9199e0c3e768bb7699bd640ddad3d6b5d0628b) 清理空上传父目录时，不再等待删除子目录后刚更新的修改时间再次过期。非空父目录、活跃上传和无法读取的记录仍受保护。

未完成上传默认仍在 **24 小时**后过期，每 **6 小时**检查清理一次。重启不是清理，空列表也不证明磁盘空间已经回收。

## 升级与回滚 {#upgrade}

1. 记录实际安装版本，固定已验收二进制或镜像摘要。备份完整 IAM 存储、配置与必需的加密材料。遵循[迁移指南](/zh/compatibility/migration/)和 [IAM 恢复流程](/zh/operations/replication/iam-upgrade/)；在线 IAM 导出不包含撤销历史。
2. 协调所有 Server 进程、写入节点与复制站点。同一 IAM 后端不要混跑新旧二进制，也不要把滚动降级视为受支持操作。更换独立 UI 或客户端不等于替换 Server 的嵌入组件。
3. 用自动化实际使用的身份测试保留期、合法保留、指定版本写入、服务账户创建／更新、自助操作显式 Deny 和 root 管理。历史不可用的到期密钥应由授权父身份重新签发，不要删除存量策略 claim。
4. 如果启用过 strict 分片列表，升级前先消除对该能力的依赖。保留已知的 bucket/key/UploadID 以便完成或取消，不要用公开列表证明完整发现、彻底取消或空间回收。
5. 验证普通与分页 LIST、PUT／完成上传的重试、OIDC/JWKS、带 TLS 检查的出站链路、复制与扫描进度。不能把错误转换成成功的空清单。参见 [TLS 指南](/zh/blog/design/go127-tls-oidc-discovery/)。
6. 单独审计既有保留期、凭据、副本与待处理删除标记。升级不会恢复被覆盖版本、丢失标签、旧保留期或已丢失的撤销历史。回到 20260916 会重新引入本轮安全缺陷。

## 剩余边界与交付证据 {#delivery}

多站点删除标记的延迟创建与崩溃后少数派残留仍由 [#217](https://github.com/pgsty/silo/issues/217) 跟踪；完整、可扩展的分片枚举与创建隔离仍是 #79 的未完成范围。LIST 恢复保留适用条件与版本历史契约。本版及本文均不承诺快照清单或新的磁盘恢复保证。

签名标签及最终 36 个发行制品均指向 `0cd388c666f8211f552604ae73448a066e9c25ce`。10 月 18 日本机验收记录核验了下载摘要、六个归档标记与六个软件包载荷、34 份构建证明、两份 Sigstore 校验清单签名、两份 RPM 签名和 12 份 SBOM。该精确源码通过了 [Go CI](https://github.com/pgsty/silo/actions/runs/39136984202)、[VulnCheck](https://github.com/pgsty/silo/actions/runs/39136984236)、[Release](https://github.com/pgsty/silo/actions/runs/39137110821) 与[软件包收尾工作流](https://github.com/pgsty/silo/actions/runs/39138591714)。

本机测试使用发行仍为 Draft 时下载的二进制，覆盖原生 Darwin 与 Linux 的 S3/IAM/STS/Object Lock、LDAP/OIDC、从 20260916 升级、桶与站点复制、结合 Console 的三站恢复、三站及四进程共享集群 STS 撤销，以及四组真实迁移（2/3 池 × rebalance/decommission）。八进程两池在滚动重启负载下完成 2,896 次全量扫描，在故障恢复负载下完成 1,270 次，未出现漏项、重复或读取内容损坏。另有三组 Linux 包生命周期与八种本地容器变体验收通过。

**本机候选验收已完成，发行现已公开发布。** 所有进程和 Docker VM 共享一台物理主机，amd64 容器使用模拟运行。Windows 与 Darwin amd64 制品仅做静态核验，没有运行时验收。加密测试使用本地测试 KMS key，不代表真实云 IAM/KMS 或最终 Server 搭配外部 KES 的验收。独立物理故障域、生产性能 SLO 和真实 systemd 开机启动未获证明。故障窗口存在请求错误与延迟；内容检查通过不等于服务零中断，也不能证明 p95 劣化低于 5%。
