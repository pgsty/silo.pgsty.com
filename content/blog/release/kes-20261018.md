**Release:** [RELEASE.2026-10-18T00-00-00Z](https://github.com/pgsty/kes/releases/tag/RELEASE.2026-10-18T00-00-00Z) · **Package:** `20261018000000.0.0` · **Source:** [`2f7e741db905`](https://github.com/pgsty/kes/commit/2f7e741db905d7ea755967b29666657d819d7ad0).

This is the first maintained PGSTY release of the Key Encryption Service. **KES is a separate service**, used when SILO needs an external key service. It is not embedded in the Server or a required dependency for unencrypted deployments. KES has been published independently; Server 20261018 remains a Draft. See the [component matrix](/compatibility/versions/).

## Changes {#changes}

- Establish PGSTY maintenance and distribution while preserving upstream copyright, attribution and third-party licenses. The executable and package remain `kes`; the module remains `github.com/minio/kes`.
- Build with **Go 1.27.2**, update dependencies and migrate AWS Secrets Manager from AWS SDK for Go v1 to **v2**. Preserve YAML fields, explicit credential precedence, configured endpoints and stored key formats. KES continues to ignore `~/.aws/config` and SDK endpoint environment overrides.
- Preserve the KES HTTP API, `MINIO_KMS_KES_*` configuration, existing root keys and encrypted objects. Existing SILO/KES integration needs no Server code change or key migration.
- Add upgrade, rollback and restart tests with SILO, OpenBao KV v2 and the Moto Secrets Manager emulator. Restart SILO at each transition so its key cache cannot hide a compatibility failure.
- Provide signed tags, build attestations, signed RPMs and non-root container images. Disable `kes update`; use versioned PGSTY artifacts, packages or images to upgrade.

## Deployment and upgrade {#upgrade}

SILO encrypts object contents; KES authenticates key requests and wraps or unwraps data keys; OpenBao persists the KES root keys. `MINIO_KMS_KES_ENDPOINT` points at **KES**, not OpenBao. The [design note](/blog/design/kes-openbao/) explains ownership, failure behavior and recovery.

Configure TLS, application identities, access policies and a persistent key store before starting KES. Containers run as UID/GID `1000:1000`; configuration and certificates must be readable by that user. Linux packages install `/usr/local/bin/kes` and do not start an unconfigured service. Development mode stores keys only in memory.

Back up the original key store and configuration before upgrading. Verify decryption of old objects, creation of new encrypted objects and readback after restarting both KES and SILO. Preserve the same root keys during rollback; restoring object data without its required keys is insufficient.

The maintained acceptance path is **SILO + PGSTY KES + OpenBao KV v2**. The KES release matrix tested SILO 20260903 and 20260916, upstream KES `2025-03-12T09-35-18Z`, and a PGSTY SDK-v1 baseline. Moto supplies local protocol/storage coverage; **real AWS IAM and service behavior have not been accepted in an AWS account**. These tests do not certify every inherited key-store backend or the final Server 20261018 artifacts. Upstream MinIO compatibility is best effort.
