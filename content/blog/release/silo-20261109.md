## Lifecycle, pools and remote tiers {#lifecycle}

- **Lifecycle across pools:** Recheck lifecycle expiry under the object lock against the key's authoritative version history and Object Lock state across **all pools**. Refuse deletion when history or lock protection lacks authoritative quorum; decommission and rebalance move versions whose expiry is refused. Approved version expiries remove every pool copy.
- **Exact-key deletion:** Restrict `ExpiredObjectAllVersions`, `DelMarkerExpiration`, and batch `retainVersions: 0` deletion to the **exact key**, preserving keys under the same prefix. Refuse whole-key purges that contain tiered or Object Lock protected versions. See [exact-key deletion](/blog/design/ilm-delete-all-exact-key/).
- **Remote tiers and restored copies:** Expire only the local restored copy when `--days` elapses without deleting the underlying tiered version. Preserve remote payloads while another pool still references them, and exclude internal tier-cleanup free versions from visible version history and lifecycle decisions.
- **Rule execution and accounting:** Apply lifecycle rules whose sole action is `DelMarkerExpiration`, report only removals that occurred, and queue healing when corrupt history prevents expiry. Lifecycle-generated delete markers and version purges are not replicated, matching S3 lifecycle semantics.
- **Pool migration:** Move versions across differing erasure layouts, migrate ILM-expired current versions during rebalance and decommission, continue decommissioning remaining buckets when one bucket fails while keeping cancellation active, and prevent `rebalance stop` panics when rebalance metadata is absent.

See [multi-pool lifecycle](/blog/design/multi-pool-lifecycle-expiry/) and [restored-copy expiry](/blog/design/restored-copy-expiry/). Upgrading does not recover objects or remote payloads deleted by an earlier release.

## Native restore, locking and reads {#restore}

Native restore downloads remote-tier data outside the object write lock, then validates ownership and publishes the restored copy under that lock. This eliminates multi-pool restore hangs, wrong-version targeting, and broken ordinary multipart-completion retries. Failed or canceled restore attempts try synchronous marker cleanup for up to 100 ms before handing off remaining work to bounded background retries, avoiding a 60-second lock wait. See [two-phase restore](/blog/design/native-restore-two-phase/).

Single-pool writes and deletes lock in the object's own erasure-set domain. `CopyObject` resolves normalized key aliases without deadlocking and waits on a contended source without holding the destination lock; ordinary bulk deletion groups run concurrently across erasure sets. Multi-pool `CreateMultipartUpload` evaluates `If-Match` and `If-None-Match` against the logical current object across pools.

Known partial drive views of an existing object return a retryable **503** instead of a false `404 NoSuchKey`. Heal dry runs (`mcli admin heal --dry-run`) preserve dangling data and propagate the dry-run flag to remote peer bucket heals. Failed writes remove empty object directories, and `xl.meta` checksum failures are classified for healing.

## Object Lock, IAM and batch authorization {#authorization}

S3 `DeleteObjects` rechecks physical version removals **inside the mutation lock** used for retention and legal-hold updates, merging protection across pools and serializing against concurrent retention or legal-hold changes ([`6ef3a52fc`](https://github.com/pgsty/silo/commit/6ef3a52fc314f07c3d8450a976a7d0639b8b211c)). Directory `null` versions are checked before bulk deletion as well. Replicated deletes preserve the target's legal hold and retention: a source purge that bypassed `GOVERNANCE` retention does not grant bypass at a target copy that still carries active retention, so replication refuses the purge and retries.

Batch expiration, key rotation, and replication enforce the authenticated submitter's local S3 data permissions throughout execution and leave Object Lock protected versions intact. Multi-pool key rotation updates the authorized copy without rendering other pool copies unreadable. Revoked or re-bound identities terminate the job; transient IAM or authorization outages pause execution with a recorded reason and bounded retry. Startup discovery retries storage outages, completed expiration jobs stay completed across restarts, and replication jobs resume scans. Inspect `mcli batch status` to distinguish `complete`, `complete-with-skips`, `paused`, and `failed`.

External authorization plugins must return HTTP `2xx` with an explicit boolean decision (`result` or `result.allow`); missing or `null` decisions, trailing JSON, and responses larger than 1 MiB are rejected, and each call is bounded to 1 minute. Verify custom authorization plugins before upgrading.

IAM rejects incomplete policy loads, keeps cached authentication available during lazy loads, and applies user edits, service-account mutations, and LDAP group refreshes directly to persisted records so stale caches cannot restore rotated credentials or resurrect deleted identities. Long-DN LDAP login on erasure sets, root Console login with LDAP enabled, and peer webhook target reloads (`logger_webhook`, `audit_webhook`, `audit_kafka`) are also repaired.

## Upgrade and rollback {#upgrade}

1. **Stop batch submissions and drain or cancel unfinished jobs before changing versions.** Unfinished legacy jobs require resubmission after every node upgrades; completed jobs remain completed. Submitter-bound manifests and progress reports use a format that 20261026 rejects: do not downgrade with unfinished new-format jobs pending. Follow the [batch upgrade checklist](/administration/batch-framework/#upgrade-20261109).
2. **Drain incompatible single-pool layouts.** If erasure sets in a single pool do not all share the same hosts (18 or more hosts with automatic layout), stop every old process before starting new ones. Old and new delete/copy lock domains do not exclude each other during a rolling restart on this layout.
3. **Pause native restores during mixed-version windows.** Upgraded nodes return `503` to `POST ?restore` while any peer is old or unreachable. Full multi-pool lifecycle and bulk Object Lock protection also require all serving nodes to run 20261109.
4. **Verify S3 data-path access through every node after restart.** `silo healthcheck ready` checks the HTTP listener and configured KMS/etcd without waiting for storage or IAM initialization, and `cluster` quorum can precede remote-drive reconnection. Run bounded signed writes and readback through every node before resuming applications, and preserve peer bootstrap (`publishNotReadyAddresses: true` on Kubernetes). See [healthcheck probes](/operations/monitoring/healthcheck-probe/#native-probe).
5. **Set `image.tag` explicitly when reusing Helm values.** `helm upgrade --reuse-values` keeps the previously saved tag; pass `--set image.tag=RELEASE.2026-11-09T00-00-00Z`.

## Costs and limits {#limits}

Safety checks read additional cross-pool metadata and refuse operations that cannot be proven safe. Physical version purges in Object Lock buckets execute sequentially through the single-object path during `DeleteObjects`, so large purge batches take longer (ordinary buckets and delete-marker creation retain the bulk path). In a bounded Linux ARM64 two-pool check, the average per-round median for 1,000 removable locked-bucket versions increased from ~202 ms to ~310 ms; steady `HEAD`/`GET` medians changed by ~+1.5% / +3.4%, and alternating `4 KiB` / `1 MiB` write rounds stayed within normal run-to-run storage variance without extra request-path syscalls. These VM directory measurements document expected safety trade-offs rather than production disk throughput.

Storage timeouts still do not prove that a disk write did not commit, and this release does not add distributed fencing or recover previously deleted data. Known open limitations remain in `ListMultipartUploads` prefix/pagination ([#79](https://github.com/pgsty/silo/issues/79)), multi-site delete-marker purges ([#217](https://github.com/pgsty/silo/issues/217)), replayed bucket creation under site replication ([PR #241](https://github.com/pgsty/silo/pull/241)), tag-only read authorization returning `403` when the object is unreadable ([#293](https://github.com/pgsty/silo/issues/293)), and upstream SDK multipart-completion retry headers (`mcli put --if-not-exists`; see [multipart completion retries](/blog/design/multipart-complete-retry/)).
