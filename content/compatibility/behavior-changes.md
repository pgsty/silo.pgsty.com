**Standard S3 applications usually switch from MinIO to SILO without code changes, and modern `xl` / `xl-single` data volumes mount in place without rewriting object data.** However, migrating from upstream MinIO to SILO requires a **coordinated full-cluster stop** (mixed-version rolling replacement across the product boundary is unsupported), and security and consistency repairs deliberately tighten deployment identity, IAM policy evaluation, request signing, Object Lock, multi-pool mutations, and background jobs.

> [!IMPORTANT] Current audited baseline: SILO 20261112
> This guide covers every user-perceivable behavior change from the upstream fork baseline [`minio/minio@27742d469462`](https://github.com/minio/minio/commit/27742d469462e1561c776f88ca7a1f26816d69e2) (`2025-12-03`, after the final upstream tag `RELEASE.2025-10-15T17-29-55Z`) through **[SILO Server 20261112](/blog/release/silo-20261112/)** (`RELEASE.2026-11-12T00-00-00Z`, source [`44e848fedf8c`](https://github.com/pgsty/silo/commit/44e848fedf8cec3d8c0da4b1aa8422390a2b7a8b), embedding **[Console v2.7.2](/blog/release/console-2.7.2/)** [`0e7953ff59c4`](https://github.com/pgsty/silo-console/commit/0e7953ff59c4a1eb77c7d203b265e6783ff18d01), paired with **[mcli 20261112](/blog/release/mcli-20261112/)** [`a37a9f054fba`](https://github.com/pgsty/mc/commit/a37a9f054fba828a0bbbceb4e9ff247ccf09c28d), `silo-pkg v3.16.1`, Helm chart `7.0.5`, and Go `1.27.4`). For the 24-category executive index, see the [Compatibility Overview](/compatibility/); for step-by-step cutover commands, see the [Migration Guide](/compatibility/migration/).

## Can an Existing MinIO Cluster Run Directly on SILO? {#takeover}

When evaluating an in-place takeover, separate three distinct questions: **whether SILO reads existing disks**, **whether nodes can be swapped one by one while serving traffic**, and **whether existing policies, integrations, and background jobs keep identical semantics afterward**:

| Scenario or Boundary                                                                                  | Verdict                                            | Behavior on SILO 20261112                                                                                                                                                                                                           | Operational Requirement                                                                                                                                |
| :---------------------------------------------------------------------------------------------------- | :------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Modern single-drive (`xl-single`) and distributed (`xl`) data volumes                                 | {{< badge text="Direct Mount" tone="success" >}}   | `.minio.sys/format.json` and XL metadata headers remain compatible; existing objects, versions, multipart uploads, encryption headers, and stored IAM records load in place without rewriting object data                           | Inspect `.minio.sys/format.json` read-only (`xl` or `xl-single`) and confirm healthy read quorum across all erasure sets before stopping old processes |
| Legacy `fs` or `gateway` directories                                                                  | {{< badge text="Unsupported" tone="danger" >}}     | Removed upstream in `2022-10-29`; SILO rejects legacy `fs` directories at startup (note: modern single-directory `server /data` uses `xl-single`, which mounts directly)                                                            | Migrate data via object export/mirror following the [FS/Gateway migration guide](/operations/deployments/baremetal-migrate-fs-gateway/)                |
| Mixed-binary rolling cluster (MinIO + SILO nodes running together)                                    | {{< badge text="Blocked" tone="danger" >}}         | Distributed bootstrap verifies peer binary checksums, private internode StorageREST removed `/rmpl` (`ReadMultiple`), and peer IAM/replication protocols advanced                                                                   | Cut over from upstream MinIO to SILO as a **coordinated full-cluster stop**, never node-by-node mixed binaries                                         |
| Single pool whose erasure sets span different host subsets (typically ≥ 18 hosts in automatic layout) | {{< badge text="Full Stop" tone="warning" >}}      | Pre-`20261109` processes routed single-pool locks to erasure set 0 instead of the target set; mixed old/new processes use disjoint lock domains and lose mutual exclusion                                                           | Drain traffic and stop every old process before starting `20261109` or later                                                                           |
| Multi-pool cluster rolling between SILO releases                                                      | {{< badge text="Drain Writes" tone="warning" >}}   | Cross-pool conditional writes, lock ordering, bulk version purges, and suspended-bucket `null`-version lock checks require all nodes on `20261112` for uniform guarantees                                                           | Drain or pause concurrent S3 writes across mixed-version multi-pool rolling windows                                                                    |
| Multi-site replication and shared IAM cutover                                                         | {{< badge text="Coordinated" tone="warning" >}}    | Durable IAM revocation tombstones (`20260916+`) and tri-state service-account inline policies (`20261112`) can be overwritten if an unupgraded peer site edits accounts and resyncs                                                 | Avoid editing service accounts or IAM policies on old sites during mixed-site rollouts; reconcile policies after all sites upgrade                     |
| Unfinished Batch jobs (`expire`, `replicate`, `keyrotate`)                                            | {{< badge text="Drain First" tone="warning" >}}    | `20261109+` writes submitter-bound `SILO-BATCH` v2 manifests and reports; legacy running/queued/paused jobs are not guaranteed to resume across the boundary, and `≤ 20261026` rejects v2 records                                   | Stop new batch submissions, let active jobs finish or cancel them before upgrading, and resubmit once all nodes run `20261112`                         |
| Native S3 archive restore (`POST ?restore`)                                                           | {{< badge text="All Nodes" tone="warning" >}}      | Two-phase lock-free restore (`20261109+`) requires every peer in the cluster to advertise the capability and be reachable; otherwise `POST ?restore` returns `503`                                                                  | Upgrade all nodes and confirm peer connectivity before running archive restores                                                                        |
| Custom IAM policies, OIDC/LDAP, TLS/KMS, and notifications                                            | {{< badge text="Audit Config" tone="info" >}}      | Object-only ARNs no longer grant 12 bucket-level writes, version deletes require `s3:DeleteObjectVersion`, self-service password change checks `admin:ChangeMyPassword`, HMAC OIDC is rejected, and legacy DB notify requires a DSN | Audit representative policies and test login, KMS decryption, replication, and event targets before reopening client traffic                           |
| Swapping back to an older binary for rollback                                                         | {{< badge text="Backup Required" tone="danger" >}} | Readable objects do not prove safe downgrade: startup, scanner passes, IAM revocations, Batch v2 manifests, and bucket tombstones update `.minio.sys` state that older binaries reject or misinterpret                              | Capture an offline consistent backup of `.minio.sys`, IAM exports, and deployment manifests before cutover; restore all peers together if rolling back |
{.matrix .wide .expand}

## Quick Check by Starting Version {#by-version}

Select your current running version to focus on the upgrade gates that apply directly to you; refer to the 12 domain tables below for full details.

{{< tabs group="upgrade-origin" default="minio" label="Select your current version" >}}
{{< tab label="From Upstream MinIO (≤ 2025-10-15)" value="minio" >}}

Migrating directly from upstream MinIO (such as the final tag `RELEASE.2025-10-15T17-29-55Z`) crosses every fork-era delivery and security boundary in one cutover:

- **Cutover mode and disk verification**: Confirm `.minio.sys/format.json` is `xl` or `xl-single`, capture an offline backup, and execute a **coordinated full-cluster stop** (do not mix MinIO and SILO nodes). See the documented [single-node migration case](/compatibility/migration/#single-node-case).
- **Deployment and artifact identity ([Section 1](#deployment))**: Switch images to `docker.io/pgsty/silo:RELEASE.2026-11-12T00-00-00Z`, server binary/systemd unit to `silo`, and client package to `mcli`. Replace hard-coded `/usr/bin/minio` paths with `silo`. Preserve Helm resource names and explicitly pin `image.tag`. Remove `admin update`, `mcli update`, and SUBNET automation.
- **IAM policies and external authentication ([Section 2](#iam), [Section 3](#object-authorization))**:
  - Statements containing only `arn:aws:s3:::bucket/*` no longer grant 12 bucket-level write actions (`PutBucketPolicy`, `PutBucketLifecycle`, `DeleteBucket`, etc.); add bare `arn:aws:s3:::bucket` to the same statement.
  - Permanent deletes carrying `versionId` require `s3:DeleteObjectVersion`; `Allow s3:*` + `Deny s3:DeleteObject` policies must also add `Deny s3:DeleteObjectVersion`.
  - Self-service password updates check `admin:ChangeMyPassword` (the built-in `readonly` policy no longer permits self-service password changes). Policy writes enforce strict JSON decoding and reject bare ARN namespace prefixes.
  - OIDC rejects symmetric `client_secret` HMAC (`HS256/384/512`) tokens and RSA JWKs above 4096 bits. Configure `MINIO_API_TRUSTED_PROXIES` when trusting `X-Forwarded-For` / `X-Real-IP` / `Forwarded`.
- **Integrations and background jobs ([Sections 8–10](#bucket-config))**: Convert legacy PostgreSQL / MySQL notification settings to `connection_string` / `dsn_string`; review per-bucket CORS rules (now actively enforced); drain unfinished Batch jobs before stopping; verify signed S3 reads/writes against every node after startup.

{{< /tab >}}
{{< tab label="From SILO 20260804–20260903" value="silo-202608-09" >}}

You have already crossed the `silo` / `mcli` rename and initial fork security gates (bare bucket ARNs, `DeleteObjectVersion`, OIDC asymmetric JWKS). Upgrading to `20261112` focuses on changes introduced since `20260916`:

- **IAM and password authorization ([Section 2](#iam))**: `20260916` split `admin:ChangeMyPassword` and introduced durable IAM revocation tombstones (follow the [IAM upgrade guide](/operations/replication/iam-upgrade/) across peer sites); `20261018` hardened delegated Admin escalation and root-derived credentials; `20261112` enforces strict policy JSON decoding and preserves service-account inline policies when omitted (`{}` resets to inheritance).
- **S3 tag headers and archive-member authorization ([Section 3](#object-authorization))**: Local and active-active proxied `GET`/`HEAD` responses omit `x-amz-tagging-count`, `X-Amz-Tagging`, and `X-Amz-Object-Lock-*` unless the caller holds the corresponding tag or lock read permission; ZIP member reads authorize the outer ZIP's stored tags without persisting an on-disk index.
- **Topology stop gates and background jobs ([Sections 6–10](#replication))**: Single-pool clusters spanning distinct host subsets across erasure sets (typically ≥ 18 hosts) require a **full stop** to align lock domains; drain or cancel unfinished Batch jobs before upgrading (`SILO-BATCH` v2 manifests); `POST ?restore` returns `503` while any peer is unupgraded; drain concurrent S3 writes across multi-pool rolling windows.
- **HTTP, TLS, and Console ([Sections 11–12](#operations))**: HTTP/1 request headers enforce an absolute read deadline; Go `1.27.4` and `-distroless` UBI CA roots apply; embedded Console advances to `v2.7.2` (cursor pagination, 10 UI languages, folder usage scans, tri-state inline-policy editor).

{{< /tab >}}
{{< tab label="From SILO 20260916–20261026" value="silo-20260916-1026" >}}

When upgrading from the September or October releases to `20261112`, check these operational gates:

- **Deployments that enabled optional `20260916` `strict` multipart listing ([Section 5](#multipart))**: Retired in `20261018+` (ignored with a startup warning); `ListMultipartUploads` uses the default cache/exact-key path without durable enumeration across restarts.
- **Single-pool lock domains, Batch v2, and native restore (`20261109` gates)**:
  - Drain and stop every old process before starting `20261112` if a single pool's erasure sets do not all share the exact same host set (normally ≥ 18 hosts);
  - Drain or cancel all unfinished Batch jobs before upgrading and resubmit afterward (`≤ 20261026` rejects `SILO-BATCH` v2 manifests);
  - Native `POST ?restore` returns `503` until every peer runs `20261109+` and is reachable.
- **`20261112` authorization, lock, and multi-pool repairs**:
  - Service-account edits preserve existing inline policies when omitted and require explicit `{}` (or turning off **Restrict beyond user policy**) to restore inheritance — avoid editing service accounts on old peer sites during rollout;
  - Strict policy JSON decoding rejects unknown fields and trailing data across IAM, STS, bucket policies, Console, and `mcli`;
  - Every explicit-`VersionId` entry in `DeleteObjects` runs sequentially through the single-object path across all buckets, increasing latency for large version purges;
  - Locked `null` versions in versioning-suspended or prefix-excluded buckets are protected against ordinary overwrites and shadowed deletes; compressed+encrypted `Range` reads and cross-pool historical self-copies are repaired.

{{< /tab >}}
{{< tab label="From SILO 20261109 → 20261112" value="silo-20261109" >}}

`20261109` already includes single-pool lock-domain alignment, `SILO-BATCH` v2 manifests, and two-phase native restore. Upgrading to `20261112` focuses on these targeted deltas (see [20261112 upgrade notes](/blog/release/silo-20261112/#upgrade)):

- **Service-account inline-policy preservation and reset (SN-2026-025)**: Updating a service account or access key with an omitted/`null` policy preserves its existing inline policy (including pre-`20261111` empty deny-all inline policies); pass `{}` or `{"Statement":[]}` explicitly to clear the inline policy and restore inheritance. Do not edit service accounts on `20261109` peer sites during a mixed-site rollout.
- **Strict policy JSON and SSE-KMS context validation**: Server, Console `v2.7.2`, and `mcli 20261112` reject unknown JSON fields, trailing payloads, and empty `Principal: {}` in policy writes; invalid `X-Amz-Server-Side-Encryption-Context` headers return `400 InvalidArgument` instead of `500`, while `keyrotate` persists KMS context and stream-rewrites legacy `XLV1` objects onto `XLV2`.
- **S3 tag headers, ZIP member authz, and signing bounds (SN-2026-022 / -023 / -024)**: Local and active-active proxied `GET`/`HEAD` responses omit `x-amz-tagging-count`, `X-Amz-Tagging`, and `X-Amz-Object-Lock-*` when tag or lock read permission is absent; tag-authorized reads preserve `5xx` storage errors on read-quorum failure instead of returning false `403` (`#294`); ZIP member reads verify outer ZIP tags in memory without mutating the object; authenticated `STREAMING-UNSIGNED-PAYLOAD-TRAILER` enforces the 15-minute skew window, and SigV4 rejects mismatched scope dates and > 64 KiB trailers.
- **Object Lock, bulk version deletes, and pools**: Versioning-suspended buckets protect locked `null` versions against overwrites and delete markers; `DeleteObjects` runs sequentially on all explicit-`VersionId` entries across all buckets; pause concurrent S3 writes across multi-pool rolling windows; fixes cover compressed+encrypted `Range` reads (`decryptSkip > 0`), cross-pool historical self-copy (`#343`), pre-`2024-04-28` `xl.meta` and `UsesDataDir` revision normalization (`#332`, `#344`), and decommission nested child-key rescans plus within-quorum offline-drive emptiness checks (`#334`).
- **Helm upgrade**: Pass `--set image.tag=RELEASE.2026-11-12T00-00-00Z` explicitly when upgrading Helm chart `7.0.5` with `--reuse-values`.

## 3. Request Signing & S3 Object Authorization {#object-authorization}

## 14. Pre-Upgrade & Rollback Checklist {#upgrade}

Follow these five steps when cutting over from upstream MinIO or upgrading an earlier SILO deployment to **SILO `20261112`**:

1. **Verify disk format, quorum health, and rollout mode**: Inspect `.minio.sys/format.json` read-only (`xl` or `xl-single`) and run `mcli admin info` to confirm healthy read quorum across every pool and erasure set. Schedule a **coordinated full-cluster stop** when migrating from upstream MinIO or when upgrading a single pool whose erasure sets span distinct host subsets (typically ≥ 18 hosts) from `≤ 20261026`; pause concurrent S3 writes across multi-pool rolling windows.
2. **Drain background jobs and capture an offline recovery point**: Stop new Batch submissions and let running, queued, or paused Batch jobs finish (or cancel them). Record exact image digests / binary versions and rendered systemd / Compose / Helm manifests, export IAM and bucket metadata (`mcli admin cluster iam export`, `mcli admin cluster bucket export`), and capture a consistent backup of `.minio.sys` and config files once writes are paused.
3. **Audit configuration, policies, and external TLS/auth**: Replace hard-coded `/usr/bin/minio` paths with `silo` and pass `--set image.tag=RELEASE.2026-11-12T00-00-00Z` with `helm upgrade --reuse-values`. Check custom IAM policies for bare bucket ARNs on the 12 bucket writes, `s3:DeleteObjectVersion`, `admin:ChangeMyPassword`, strict JSON syntax, and service-account inline restrictions; verify asymmetric OIDC JWKS (RSA ≤ 4096 bits), SQL notification DSNs, `MINIO_API_TRUSTED_PROXIES`, and external CA roots.
4. **Cut over atomically and verify the S3 data path on every node**: After `silo healthcheck ready` succeeds, run bounded signed S3 write, read, conditional, and `Range` checks **directly through every individual node** (covering representative multipart, encrypted, and compressed historical objects), then validate Console login, representative sub-user credentials, replication queues, and notification delivery.
5. **Resume background operations and reconcile multi-site policies**: Once every cluster node and replicated peer site is running `20261112`, resubmit Batch jobs, re-enable archive `POST ?restore` workflows, and verify effective service-account policies across replicated sites.
{.steps}

> [!CAUTION] Hard boundary for downgrades and rollback
> **Mounting existing disks in place does not mean you can swap back to an older binary later without restoring state.** Startup routines, background scanners, IAM edits (durable revocation tombstones and tri-state inline policies), `SILO-BATCH` v2 manifests, and bucket metadata tombstones update `.minio.sys` state in ways older MinIO or SILO binaries may reject or misinterpret. If you must roll back, restore your pre-cutover consistent backup across all participating nodes and replication peers together — never downgrade a single node's binary or image in isolation.
