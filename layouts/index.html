FAQ

{{ if $zh }}常见问题，直接回答{{ else }}Questions we get asked{{ end }}

{{ if $zh }}简短的回答，附上通往详细版本的链接。{{ else }}Short answers. The details are behind the links.{{ end }}

Q1{{ if $zh }}这个项目为什么存在？{{ else }}Why does this project exist?{{ end }}

{{ if $zh }}因为上游收缩了社区版：控制台被削减、预编译制品停发、社区仓库被归档。Silo 的存在是为了让一个持续维护、功能完整的 S3 兼容社区对象存储继续存在——Pigsty 自己在生产环境用它承载 PostgreSQL 备份。完整的理由与承诺见《Silo 宣言》。{{ else }}Upstream wound down its community edition: the web console was cut back to a stub, prebuilt binaries stopped, and the server repository was archived. Pigsty runs its own PostgreSQL backups on this code, so it needed a maintainer either way. Everything else follows from that. The reasoning is written out in the PGSTY SILO Manifesto.{{ end }}

Q2{{ if $zh }}它解决什么问题？{{ else }}What problem does it solve?{{ end }}

{{ if $zh }}让既有的 MinIO 兼容部署继续可用：可直接下载的版本化二进制与软件包、附公告的安全修复、完整的 Web 控制台——不需要自行构建，也不需要商业许可。它做的是维护与延续，不是新的产品路线图。{{ else }}It keeps existing MinIO-compatible deployments running: versioned binaries and packages you can download, security fixes with public advisories, and the full web console. No build step and no commercial license. This is maintenance work, not a new product.{{ end }}

Q3{{ if $zh }}你们承诺什么？{{ else }}What do you promise?{{ end }}

{{ if $zh }}一份刻意收窄的清单：永远 AGPLv3 且无 CLA（仅 DCO）；无付费墙、无注册墙、无遥测；通常每 1–2 个月发一版，最长一个季度；每项安全修复都附公开公告。我们拒绝承诺的——修复时限 SLA、上游路线图的延续——也以同样的认真写在《宣言》里。{{ else }}A short list, kept short on purpose. AGPLv3 with no CLA: contributions come in under DCO sign-off, so copyright stays with each author. No paywalls, no registration walls, no telemetry. A release every one to two months, at most a quarter apart. A public advisory for every security fix we ship. The Manifesto also lists what we refuse to promise, such as fix-time SLAs.{{ end }}

Q4{{ if $zh }}谁在维护这个分叉？{{ else }}Who maintains this fork?{{ end }}

{{ if $zh }}实名回答：这个分叉以 PGSTY 组织的名义维护，实际维护者是 冯若航（Vonng）——PostgreSQL 发行版 Pigsty 的作者。他曾部署并管理 25PB 规模的 MinIO 集群，并拥有资深的软件打包经验。延续性安排提前写在《宣言》第九条。{{ else }}One person, named. The fork is maintained under the PGSTY organization by Ruohang Feng (Vonng), who wrote the Pigsty PostgreSQL distribution. He has deployed and run a 25 PB MinIO cluster, and does the packaging and releases here. Article 9 of the Manifesto says in advance what happens if that arrangement ends.{{ end }}

Q5{{ if $zh }}Coding Agent 在项目中扮演什么角色？{{ else }}What role do coding agents play?{{ end }}

{{ if $zh }}Agent 是功能开发与代码 Review 的主力。与之配套的承诺是：每一个变更都必须通过 CI 与人工审核，所有建设性变更都要经过人类的利弊权衡才会合入；Agent 的完整思考记录会归档留存，其利弊权衡也会作为设计文档归档，以备查阅。安全纪事与发布说明里可以看到这套工作方式的公开产出。{{ else }}Most of the code, and most of the first-pass review, is written by coding agents. A human reads every diff, decides the trade-offs, and merges; nothing lands without CI and that review. We keep the agents' working notes and trade-off write-ups, because when a fix turns out to be wrong, the reasoning behind it is the thing you want. The security advisories and release notes are what this arrangement produces in public. Judge it on those.{{ end }}

Q6{{ if $zh }}磁盘格式会变化吗？{{ else }}Will the on-disk format change?{{ end }}

{{ if $zh }}不会。.minio.sys 元数据目录与对象布局保持上游原样，由 CI 兼容性门禁冻结，与 MinIO 双向互通。新增能力默认不触碰磁盘格式；任何例外都将是显式可选、启用前明确标注的。参见兼容性审计。{{ else }}No. The .minio.sys metadata directory and the object layout are unchanged from upstream, held in place by a CI compatibility check, and tested for interoperability with MinIO. New features do not touch the on-disk format; if one ever has to, it will be opt-in and marked non-reversible before you can turn it on. The compatibility audit has the details.{{ end }}

Q7{{ if $zh }}兼容性怎么样？{{ else }}How compatible is it?{{ end }}

{{ if $zh }}可以原地替换：S3 API、MINIO_* 环境变量、minio_* 指标、x-minio-* 头与 /minio/* 路由全部不变——容器部署里迁移只需改一个镜像名，且有经过演练的回滚路径。所有差异逐版本记录在兼容性说明中；迁移指南覆盖 Docker 与软件包安装。{{ else }}The S3 API, MINIO_* environment variables, minio_* metrics, x-minio-* headers, and /minio/* routes are unchanged. For a container deployment that usually means changing the image name and keeping the same volume. The differences that do exist are recorded per version in the compatibility notes, and the migration guide covers Docker, packages, and the rollback path.{{ end }}

Q8{{ if $zh }}可以用于生产环境吗？{{ else }}Can I run it in production?{{ end }}

{{ if $zh }}可以——这就是我们自己在生产环境中使用的版本：Pigsty 的生产 PostgreSQL 备份就跑在 Silo 上，你下载的制品与我们线上运行的是同一批。本页还列出了带公开出处的第三方采用记录；照例建议锁定版本、先用自己的负载验证，并保留迁移指南中演练过的回滚路径。{{ else }}Yes, with the usual caveats. Pigsty's production PostgreSQL backups run on Silo, and this page links third-party reports from people running it elsewhere. That is evidence, not a warranty. Pin a release, test it against your own workload, and rehearse the rollback in the migration guide before you need it.{{ end }}

Q9{{ if $zh }}AGPL 对我的应用意味着什么？{{ else }}What does the AGPL mean for my app?{{ end }}

{{ if $zh }}先说结论：我们承诺永远不会以 AGPLv3 对你发起追索，也绝不会拿协议为难你。Silo 与上游一样采用 AGPLv3 且永不变更；我们公开的立场（立场，而非法律意见）是：通过 S3 API 使用 Silo 不构成衍生作品。由于没有 CLA、只接受 DCO 签署的贡献，连重新授权本身都在结构上不可能——见《宣言》第三条。{{ else }}Silo carries AGPLv3, the same license as the upstream it forked. Our position (a position, not legal advice) is that using Silo through its S3 API does not make your application a derivative work, and we will not use the license as a threat or a sales instrument. We also could not relicense it if we wanted to: there is no CLA, contributions come in under DCO, and copyright stays spread across everyone who wrote a line. Article 3 of the Manifesto has the full statement.{{ end }}

Q10{{ if $zh }}如果项目停止维护会怎样？{{ else }}What if maintenance stops one day?{{ end }}

{{ if $zh }}我们会尽最大努力，确保所有已发布的制品与文档持续可用。构建过程完整文档化并附溯源证明，任何人都能在没有我们的情况下从源码重建等价制品；若停止积极维护超过六个月，我们会公开声明并妥善归档——完整的退出安排见《宣言》第九条。{{ else }}Released artifacts and documentation are meant to stay up, and we will keep them up as long as we can. The build is documented and provenance-attested, so anyone can rebuild equivalent artifacts from source without us. That part does not depend on us being around. If active maintenance stops for six months, we will say so publicly and archive the project rather than let it go quiet. Article 9 of the Manifesto has the exit plan.{{ end }}
